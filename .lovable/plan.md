

# Аудит ролей и прав + план развития

## Что есть сейчас

**3 уровня ролей (3 разных таблицы):**

```text
┌──────────────────────────────────────────────────────────────────┐
│ 1) user_roles  — глобальная роль входа (one per user)            │
│    enum app_role: admin | organization | student                 │
│                   | sales_manager | company                      │
│    → определяет, в какой кабинет попадает пользователь           │
├──────────────────────────────────────────────────────────────────┤
│ 2) admin_staff — сотрудники платформы (внутри роли admin)        │
│    role: super_admin | admin | sales_manager | viewer            │
│    → описание есть, но НИГДЕ не проверяется в коде/RLS           │
├──────────────────────────────────────────────────────────────────┤
│ 3) org_staff   — сотрудники организации (внутри роли organization)│
│    role: owner | admin | school_editor | course_editor | teacher │
│    sections_access: jsonb (доступ к разделам)                    │
│    → описание и UI есть, но sections_access НЕ применяется в UI  │
└──────────────────────────────────────────────────────────────────┘
```

**Глобальная роль `company`** — отдельный кабинет компании-клиента (B2B-обучение сотрудников). Выдаётся через `companies.user_id` + запись в `user_roles`. Сейчас работает: вход, дашборд, заказы, документы.

**Глобальная роль `sales_manager`** — отдельный кабинет `/sales`. Связь с CRM через таблицу `sales_managers` (id ↔ leads/proposals/contracts/tasks).

## Что плохо / отсутствует

### Критично (фактически не работает)
1. **`admin_staff.role` — фасад без сути.** В RLS и ProtectedRoute проверяется только `has_role('admin')`. То есть «Наблюдатель» и «Менеджер по продажам» из admin_staff видят ровно то же, что супер-админ. Никакой защиты.
2. **`org_staff.sections_access` нигде не читается.** В UI перечислены роли и «6 из 9 разделов», но при заходе сотрудника организации — он либо видит всё (если у него `user_roles.role='organization'`), либо ничего. Промежуточных прав нет.
3. **Нет связки `admin_staff.role='sales_manager'` ↔ `sales_managers`.** Это два независимых списка. Менеджера приходится заводить дважды, и admin_staff/sales_manager не дают друг другу прав.
4. **Нет audit-привязки** «кто из менеджеров что сделал в админке» — все действия пишутся как «admin».

### Средне
5. **Нет ролей для `company`-кабинета.** Сейчас компания = один логин. Если у клиента 3 HR-специалиста, они шарят пароль. Нужны `company_staff` (HR / руководитель отдела / наблюдатель).
6. **Нет приглашений по email** — добавить сотрудника можно только если он уже зарегистрирован. Нет invite-токена с автосозданием.
7. **Нет «Журнала смены ролей»** — когда и кто кому повысил/понизил роль.
8. **Нет UI-матрицы прав** «роль × раздел» с галочками. Сейчас права захардкожены `accessLabel: "6 из 9 разделов"`.

### Полезные фичи
9. **2FA для super_admin** (опционально, через TOTP в auth).
10. **Передача владения** организацией другому сотруднику (owner → owner).
11. **Временные роли** — `expires_at` в org_staff/admin_staff (доступ на 30 дней для подрядчика).
12. **Роль «Преподаватель»** должна автоматически видеть только свои курсы + домашние задания только своих учеников (сейчас видит всё).

## План работ — 3 этапа

### Этап 1. Приземлить уже описанные роли (фундамент)
- Добавить `permission_matrix` (константа в `src/constants/rolePermissions.ts`) — единый источник правды «роль → разрешения». Покрывает org_staff и admin_staff.
- Хук `useStaffPermissions()` — отдаёт `{ can('billing.write'), can('courses.read'), … }` для текущего пользователя на основе его записи в org_staff/admin_staff + глобальной роли.
- Защитить sidebar организации и админ-панели: пункты меню скрываются по `can('section.read')`.
- RLS-функции `has_admin_staff_role(role)` и `has_org_staff_permission(perm)` + применить на критичных таблицах (sales_*, billing_*, org_billing_documents, broadcast).
- Привязать `admin_staff` к `sales_managers`: при добавлении сотрудника с ролью `sales_manager` автоматически создаётся запись в `sales_managers`; при удалении — деактивируется.

### Этап 2. UX для управления ролями
- Заменить карточки ролей в `AdminStaffTab` и `StaffManager` на **матрицу «роль × раздел»** с реальными чекбоксами (по умолчанию шаблон, можно переопределить per-user через `sections_access`).
- **Кастомные роли** организации: возможность создать роль «Куратор группы» с произвольным набором прав (новая таблица `org_custom_roles`).
- **Приглашения по email** (новая таблица `staff_invitations`): админ вводит email → SMTP письмо с magic-link → автоматическое создание профиля + назначение роли.
- **Журнал смены ролей** (`role_audit_log`) с UI на странице сотрудника: «12.04 admin@... повысил Иванова с teacher до admin».
- **Временные роли** — поле `expires_at`, ночной cron снимает истёкшие.

### Этап 3. Расширения
- **`company_staff`** — несколько пользователей внутри одного company-кабинета с ролями `owner`, `hr`, `viewer`.
- **«Передача владения»** организацией / компанией с подтверждением по email.
- **Преподавательские ограничения**: фильтрация курсов и домашних заданий по `org_staff.user_id` (RLS + UI).
- **2FA (TOTP)** для super_admin через Lovable Cloud auth.
- **Карточка «Кто что может»** в Help Center — генерится из `permission_matrix`.

## Технические детали

- Новые таблицы: `staff_invitations`, `role_audit_log`, `org_custom_roles`, опц. `company_staff`.
- Новые SQL-функции (SECURITY DEFINER): `has_admin_staff_role(_role)`, `has_org_staff_permission(_perm)`, `accept_staff_invitation(_token)`, `expire_staff_roles()` (cron).
- Новый файл `src/constants/rolePermissions.ts` — матрица. `src/hooks/useStaffPermissions.ts` — клиентский гард. Обёртка `<RequirePerm perm="billing.write">`.
- Edge-функция `send-staff-invitation` (SMTP через существующий механизм).
- Cron `expire-staff-roles-daily` (00:00 UTC).
- Триггер `sync_admin_staff_to_sales_managers` — создаёт/деактивирует запись.
