
## Что просит пользователь
На стороне организации, когда клиент прислал правки к договору (статус `changes_requested`), сейчас нет UI для работы с этими правками. Видны только карточки комментариев справа с кнопкой "+ Добавить", но нет:
1. Возможности **принять** или **отклонить** каждую правку клиента (accept / reject).
2. Возможности **подписать документ как есть** (если правки устроили или клиент согласился без правок).
3. Возможности **скорректировать договор и отправить новую версию** клиенту на повторное согласование.
4. Понимания общего workflow согласования правок.

## Что нужно изучить перед планом
Мне нужно посмотреть текущее состояние компонентов согласования со стороны организации, чтобы спланировать точечно:
- `CounterpartiesSection.tsx` — где раскрывается документ с правками.
- Компонент, который рендерит правый список комментариев со скриншота.
- Структуру таблиц `signature_comments`, `document_signatures`, `document_revisions` (есть ли поля статуса по каждому комментарию, версионирование).
- Существующие edge-функции для подписания / отправки новой ревизии.

## Решение (в общих чертах)

### 1. Панель работы с правками клиента
В режиме просмотра документа со статусом `changes_requested` для организации:
- На каждой карточке комментария справа добавить кнопки:
  - **Принять** (зелёная) — правка считается согласованной, она будет применена к новой ревизии.
  - **Отклонить** (красная) — правка отклоняется, в документ не уходит, клиенту видно "отклонено" с возможностью комментария.
  - **Ответить** — короткий текстовый ответ к комментарию (для обсуждения).
- Статус комментария отображать визуально (галочка / крест / в обсуждении).

Кнопка "+ Добавить" со скриншота — это, похоже, "добавить свой контр-комментарий". Её оставляем, но переоформляем в одном ряду с принять/отклонить, чтобы не путать.

### 2. Действия над всем документом
Сверху или снизу панели правок добавить блок действий для организации:
- **Подписать как есть** — если все правки приняты или клиент в итоге согласился, организация подписывает документ (текущая ревизия становится финальной, документ уходит в `signed`/ожидание подписи клиента).
- **Сформировать новую версию и отправить клиенту** — система берёт принятые правки, применяет их к тексту, создаёт новую `document_revision`, статус `pending_signature`/`changes_applied`, клиенту уходит уведомление и ссылка на новую версию.
- **Отклонить все правки и вернуть клиенту** — отправить документ обратно без изменений с пояснением.

### 3. Версионирование
- Хранить историю ревизий в `document_revisions` (если её ещё нет — добавить).
- Каждый комментарий привязан к `revision_id`, чтобы при формировании новой версии было понятно, какие правки уже учтены.
- В UI добавить переключатель "Версия 1 / Версия 2 / …" или хотя бы пометку "правки к версии N".

### 4. Уведомления
- При действии "Отправить новую версию клиенту" — отправлять клиенту email + создавать одно агрегированное уведомление (как уже делали для обратной стороны).
- При "Подписать как есть" — стандартный флоу подписания.
- При "Отклонить все" — одно уведомление клиенту "Правки отклонены, документ возвращён".
