

# План: реорганизация сайдбара «Документы» + аудит функционала

## 1. Новая структура сайдбара

Группируем существующие пункты в 2 крупных раздела (плюс короткая шапка для KPI и контрагентов — это «корневые» вещи, без которых всё остальное теряет смысл).

```text
ДОКУМЕНТЫ (вкладка)
│
├─ Сводка / KPI                       ← корень, остаётся сверху
├─ Контрагенты                        ← корень, главный экран
├─ Входящие                           ← корень
│
├─ ── ПРОДАЖИ ──────────────────
│   ├─ Коммерч. предложения
│   ├─ Договоры (продажи)
│   └─ Подписания                     ← переезжает сюда (по сути это про сделки)
│
├─ ── ДОКУМЕНТЫ ОРГАНИЗАЦИИ ──
│   ├─ Программы
│   ├─ Журналы
│   ├─ ФИС ФРДО
│   ├─ Свидетельства
│   ├─ Дипломы
│   ├─ Удостоверения
│   ├─ Протоколы АК
│   ├─ Приказы
│   ├─ Документы орг. (273-ФЗ)        ← обязательные документы юрлица
│   └─ Запросы ПД (152-ФЗ)
│
└─ ── СЛУЖЕБНОЕ ──────────────
    ├─ Конструктор шаблонов
    └─ Корзина
```

### Что меняется в коде

- Файл **`src/components/organization/tabs/DocumentsTab.tsx`** — массив `NAV_ITEMS`:
  - переименовать группы: `platform` → `root`, `docs` → `org_docs`, `commerce` → `sales`, `tools` → `service`
  - перенести `signatures` в группу `sales` (сейчас в `tools`)
  - перенести `org`, `pd_requests` в группу `org_docs`
  - убрать из `tools`: `programs`, `journals`, `frdo` → они уезжают в `org_docs`
  - оставить в `service` только `constructor` и `recycle_bin`
  - заголовки групп: `«Продажи»`, `«Документы организации»`, `«Служебное»` (root без заголовка)
- Порядок NAV_ITEMS пересобрать в порядке схемы выше.
- Группы визуально подчеркнуть: жирный label-заголовок над каждой группой (текущий стиль `text-[10px] uppercase` оставляем — он уже подходит).

Других файлов трогать не нужно — `useDocumentsTab.ts` уже знает все эти sub-tab id, рендер в `DocumentsTab.tsx` уже на месте.

## 2. Глобальный аудит функционала вкладки

### Что уже работает (подтверждено по коду)

| Сценарий | Где | Статус |
|---|---|---|
| Загрузка своего договора (PDF/DOCX до 20 МБ) → отправка админу Синтагмы на согласование | `ExternalContractUploader` + `CounterpartiesSection.renderPlatformContracts` | ✅ работает |
| ПЭП-подписание договора с компанией/учеником (с двусторонней опцией) | `SendForSigningDialog` + `SignaturesJournal` | ✅ работает |
| Цифровая печать и подпись (загрузка PNG в Конструкторе) | `ConstructorSection` + `useDocumentsTab.handleStampUpload/handleSignatureUpload` | ✅ работает, автоподстановка в шаблоны |
| Хранение всех договоров с возможностью скачать/просмотреть | `CounterpartiesSection` + `org-documents` storage + версионирование `useOrgDocumentVersions` | ✅ работает |
| Журнал подписаний с протоколом-сертификатом ПЭП | `SignaturesJournal` + `generate-signature-certificate` edge | ✅ работает |
| Share-ссылки на документы со сроком/лимитом скачиваний | `OrgDocumentShareDialog` | ✅ работает |
| Корзина с soft-delete на 30 дней | `RecycleBinManager` | ✅ работает |
| KPI-дашборд документооборота с deep-link в нужную вкладку | `DocumentsKpiDashboard` | ✅ работает |

**Ответ на ваш вопрос:** да, вы поняли правильно. Любая организация может:
1. Загрузить свой договор (PDF/DOCX) в раздел **Контрагенты → Синтагма** — администратор Синтагмы получит его на согласование, внесёт правки и вернёт на ПЭП. Это для договоров **с самой Синтагмой**.
2. Для **отправки клиенту** (своей компании или ученику) — выбрать нужного контрагента в списке и нажать «Отправить на подписание»: документ уйдёт по email, печать/подпись организации подставятся автоматически из Конструктора, получатель подпишет ПЭП-кодом, и в журнале **Подписания** сохранится сертификат с IP, временем и хэшем.
3. Все договоры (входящие и исходящие) хранятся в `org-documents` с версионированием — скачать и посмотреть можно всегда.

### Что не доделано / можно улучшить

| Проблема | Где | Приоритет | Что сделать |
|---|---|---|---|
| **Нет публичного экрана «всё про одного контрагента»** — карточка компании показывает договоры/счета/акты только в кабинете компании (`CompanyDocumentsTab`), у организации нет одного места «вся история с этим клиентом» | `CounterpartiesSection` | средний | Добавить вкладку «История» рядом с «Договоры/Счета/Закрывающие» — тайм-лайн всех событий (подписания, отправки, оплаты) |
| **Нет массовой отправки на ПЭП** — каждый договор отправляется по одному | `SendForSigningDialog` | средний | Кнопка «Отправить пачкой» в журнале договоров с выбором получателей |
| **Нет напоминания «договор не подписан N дней»** для исходящих | `SignaturesJournal` | низкий | Edge cron `process-signature-reminders` (по аналогии с `invoice-payment-reminders`) |
| **Нет фильтра по контрагенту в Подписаниях** — только по статусу | `SignaturesJournal` | низкий | Селект «Получатель» |
| **Печать/подпись хранятся в публичном бакете** (по `useDocumentsTab.handleStampUpload`) — это PII-чувствительные артефакты | `useDocumentsTab.ts` | **высокий** | Перенести в приватный бакет с подписанными URL |
| **Нет «отзыва» отправленного на подпись документа** (только удаление из своего списка через `hide_signature_for_viewer`) | `SignaturesJournal` | средний | RPC `revoke_signature` со статусом `revoked` |
| **Нет напоминания об истечении срока самого ПЭП-токена** для входящих (есть для подписания, не для срока действия) | KPI | низкий | Колонка "истекает через" в Подписаниях |
| **Конструктор шаблонов не имеет превью с подставленными реквизитами** перед отправкой | `ConstructorSection` | средний | Кнопка «Предпросмотр с реквизитами» |
| **Запросы ПД (152-ФЗ)** — нет автоматического создания при действиях ученика (отзыв согласия, удаление аккаунта) | `DataSubjectRequestsManager` | средний | Хук в кабинете ученика на действие «Удалить мои данные» |
| **Входящие документы** не связаны с исходящими договорами (нельзя сказать «это подписанный экземпляр договора №123») | `IncomingDocumentsManager` | средний | FK `linked_signature_id` + UI «привязать к договору» |
| **Корзина** очищает не сам storage, а только запись в БД — файлы накапливаются | `RecycleBinManager` | высокий | Cron `purge-recycle-bin-storage` после 30 дней |
