
## Что реально сломано
Предыдущие правки не дали точности, потому что сама стратегия была неверной:
1. Сейчас вставка привязана к **flat-text offset** по всему DOCX-HTML. В конвертированном документе текст разбит на много `span/strong/em`, поэтому клик “после слова” и реальная точка вставки часто расходятся.
2. Вставка вводится во **всплывающем textarea вне документа**, а потом “дорисовывается” обратно в текст. Из‑за этого пользователь не редактирует прямо в месте вставки и не видит настоящий результат.
3. `insert` рендерится как простой inline `<ins>`, поэтому `Enter` не работает как нормальный перенос/новый пункт.

## Новый подход
Нужно перестать угадывать позицию через общий offset и сделать для вставки **настоящий inline-редактор внутри документа**.

### 1. Вставка не по offset, а по точному DOM-якорю
В `ReviewableDocument.tsx` для `insert` перейти на anchor вида:
- `path` до конкретного text-node / узла,
- `offset` внутри него,
- `affinity: before | after` для кликов на границах между `span`/словами.

`startOffset/endOffset` оставить как fallback для старых комментариев, но новые insert-якоря сохранять уже в DOM-anchor формате внутри `position_anchor`.

### 2. Вместо маркера + попапа — встроенный редактор в самом тексте
При клике “Добавить пункт здесь”:
- вставлять **временный inline draft-блок прямо в документ** в точке клика;
- внутри него — `contentEditable`/редактор с настоящим курсором;
- пользователь печатает **сразу в том месте**, где будет правка;
- соседний текст физически раздвигается, поэтому сразу видно, куда именно попадает вставка.

Это убирает рассинхрон “маркер в одном месте, текст в другом”.

### 3. Нормальный Enter
Для draft-редактора:
- `Enter` создаёт перенос строки / новый пункт внутри вставки;
- отображение через `white-space: pre-wrap`;
- при сохранении текст сохраняется с `\n`;
- при рендере:
  - однострочная вставка — inline зелёный `<ins>`;
  - многострочная вставка — блочная зелёная вставка с сохранением переносов.

### 4. Точное визуальное поведение
- клик в текст → появляется каретка/мини-редактор ровно в точке;
- повторный клик в другое место до сохранения → draft переезжает;
- `Esc`/отмена → draft удаляется;
- после сохранения всё состояние чистится, чтобы можно было сразу делать следующую правку.

### 5. Рендер уже сохранённых insert-правок
Для сохранённых `insert` больше не использовать `insertAtOffset` как основной механизм.
Нужно:
- находить DOM-позицию по `path + offset + affinity`,
- вставлять `<ins>` именно туда,
- для multiline вставок рендерить содержимое с переносами, а не склеивать в одну строку.

## Этапы
1. Убрать для новых insert зависимость от flat offsets и ввести DOM-anchor.
2. Заменить popup-вставку на inline draft editor внутри документа.
3. Добавить поддержку `Enter`, переносов строк и многострочного рендера.
4. Переписать отрисовку сохранённых insert-правок по DOM-anchor.
5. Починить сброс состояния, чтобы можно было подряд добавлять много правок.
6. Проверить сценарии:
   - клик после слова “период” → текст появляется ровно там;
   - `Enter` создаёт новый пункт;
   - вставка между строками/абзацами;
   - после сохранения можно сразу делать следующую вставку.

## Технические детали
- Старые комментарии оставить совместимыми: если у insert нет `path`, использовать старый `startOffset` как fallback.
- Для draft-редактора лучше сделать отдельный временный DOM-узел/React overlay-anchor внутри документа, а не `fixed`-маркер.
- Для boundary-кейсов между соседними `span` хранить `affinity`, иначе вставка снова будет “прыгать” влево/вправо.
- Для multiline insert не использовать обычный `textContent` без сохранения переносов — нужен рендер с `white-space: pre-wrap` или разбиением на строки/`<br>`.

## Результат
После исправления пользователь будет кликать в точное место документа, сразу печатать прямо там, видеть как текст раздвигается в реальном месте вставки, использовать `Enter` для нового пункта и без залипания добавлять несколько правок подряд.
