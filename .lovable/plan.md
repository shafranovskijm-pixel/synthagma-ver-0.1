

# План: единое и надёжное переключение между ключами GigaChat

## Что сейчас работает
В общем клиенте `supabase/functions/_shared/gigachat-client.ts` уже реализован пул из 3 слотов (`GIGACHAT_AUTH_KEY`, `GIGACHAT_AUTH_KEY_2`, `GIGACHAT_AUTH_KEY_3`), кэширование OAuth-токена на каждый слот, авто-фолбэк по моделям (`GigaChat-Max → Pro → Lite`) и по слотам, ретрай 429 с экспоненциальной паузой, round-robin для пакетных задач и финальный фолбэк на Lovable AI (Gemini). Все 3 ключа реально настроены в секретах.

Этим клиентом уже пользуются: `gigachat`, `bulk-pipeline`, `generate-course-structure`, `generate-lesson-content`, `demo-fill-lesson`, `student-chat`, `review-course`. Там переключение работает правильно.

## Что не так и приводит к жалобам пользователей

Три edge-функции **не используют общий клиент** и переключаются криво:

### 1. `support-chat` (бот техподдержки в углу сайта)
```ts
const authKey = Deno.env.get("GIGACHAT_AUTH_KEY") 
             || Deno.env.get("GIGACHAT_AUTH_KEY_2") 
             || Deno.env.get("GIGACHAT_AUTH_KEY_3");
```
Берёт **только первый существующий ключ** и ходит только по нему. Если на нём кончились токены (402) или 429 — никакого перехода на 2-й/3-й ключ нет, бот молча падает на Lovable AI или отвечает «Извините, не удалось…».

### 2. `generate-image` (отдельная функция картинок для курсов)
Реализует «slot pinning» — закрепляет запрос за одним слотом и ретраит его на 429, **но при 402 (исчерпание токенов) или прочих ошибках на другие слоты НЕ переключается**. То есть как только на закреплённом ключе кончатся токены — все картинки этой организации перестают генериться, хотя у других ключей токены ещё есть.

### 3. `generate-course-content` (картинки внутри массовой генерации курса)
Имеет собственный round-robin (`gigaChatImageSlotCounter`), но 402 явно не отлавливается — слот считается «временно сбойным» и через короткое время к нему опять возвращаются. Дублирует логику пула, расходящуюся с общей.

Кроме того, в общем клиенте есть мелкая шероховатость: при `[MODERATION]` запрос НЕ перепрыгивает на другие GigaChat-слоты (это правильно — модерация одинаковая на всех ключах), но при ошибке `429` в режиме round-robin сейчас сразу пробуется следующий канал, без короткой паузы — это можно сделать чуть аккуратнее.

## Что делаю

### A. `support-chat`: переключение ключей и фолбэк
Заменяю самописный `callGigaChat` в `support-chat/index.ts` на вызов общего клиента:
```ts
import { callAI } from "../_shared/gigachat-client.ts";
...
const { text } = await callAI(
  [{ role: "system", content: SYSTEM_PROMPT }, ...messages],
  1024,
  "gigachat",          // preferredProvider — пробует все 3 слота, потом Lovable AI
  "GigaChat-Pro",
  "google/gemini-2.5-flash",
);
```
Теперь, если первый ключ исчерпан (402) или 429 — автоматически идёт на 2-й, 3-й, и финально на Gemini. Пользователь поддержки всегда получит ответ.

### B. `generate-image`: переключение слотов на 402
В функции (`supabase/functions/generate-image/index.ts`) меняю стратегию:
- **Не закрепляю** жёстко на один слот; `slotIndex` (если пришёл) — это лишь стартовый слот.
- При ошибках **402 / исчерпание токенов / 5xx** — перехожу к следующему слоту по кругу.
- При **429** — сначала ретраю тот же слот с бэкоффом (как сейчас), но не более 2 раз; затем тоже переключаюсь на следующий.
- Если все 3 слота вернули 402/exhausted — пробую **Lovable AI** (`gemini-3.1-flash-image-preview`) как финальный фолбэк (логика уже есть в `generate-course-content`).
- Сохраняю «slot pinning»-эффект через `slotIndex % 3` как стартовое смещение, чтобы параллельные задачи распределялись.

### C. `generate-course-content`: использовать пул и ловить 402 явно
В `generateImageWithGigaChat` добавляю распознавание 402/429 по статусу ответа OAuth и chat completions: вместо `return null` бросаю типизированную ошибку, чтобы внешний `generateImage` знал — «слот мёртв на этот запуск, не возвращаемся к нему». Заведу локальный `Set` «мёртвых» слотов на время одного запуска генерации курса.

### D. Общий клиент — мелкая надёжность
В `_shared/gigachat-client.ts`:
- В `callAIRoundRobin` при `429` добавляю короткую паузу (1 сек) перед переключением на следующий канал — чтобы не «штормить» тот же ключ соседним вызовом, который уже стоит в очереди.
- Логи: добавляю в каждое сообщение об ошибке/успехе слот-номер и причину переключения, чтобы в `edge-function-logs` было видно, **почему** перешли с slot-0 → slot-1.

### E. Память
Дополню `mem://architecture/ai-provider-strategy` правилом: «Все edge-функции, которые ходят в GigaChat, обязаны идти через `_shared/gigachat-client.ts` (`callAI`/`callGigaChat`). Самописные клиенты с одним ключом запрещены — они приводят к падению при исчерпании токенов на одном ключе.»

## Что НЕ меняю
- Не трогаю функции, которые уже используют общий клиент (`gigachat`, `bulk-pipeline`, `generate-course-structure`, `generate-lesson-content`, `demo-fill-lesson`, `student-chat`, `review-course`) — там переключение работает.
- Не меняю бизнес-логику фронтенда (`useAiGenerationLimit`, тарифные лимиты бесплатного плана) — это отдельная история.
- Не меняю SaluteSpeech-ключи (там уже round-robin реализован, проблем нет).
- Не добавляю новый 4-й ключ — работаем с тремя имеющимися.

## Файлы

### Правки
- `supabase/functions/support-chat/index.ts` — выпилить локальный `callGigaChat`, перейти на `callAI` из общего клиента.
- `supabase/functions/generate-image/index.ts` — после неудачи на пин-слоте перебирать остальные слоты, добавить фолбэк на Lovable AI.
- `supabase/functions/generate-course-content/index.ts` — в `generateImage`/`generateImageWithGigaChat` уважать 402 (мёртвый слот в рамках задачи), синхронизировать поведение с общим пулом.
- `supabase/functions/_shared/gigachat-client.ts` — небольшая пауза при 429 в round-robin + улучшенные логи переключения слотов.
- `mem://architecture/ai-provider-strategy` — короткое правило про обязательное использование общего клиента.

### Без изменений
- Фронтенд (никаких).
- Конфиг secrets (все 3 ключа уже есть).
- Тарифы и лимиты.

## Как проверим после внедрения
- Откроем `supabase--edge_function_logs` для `support-chat`, `generate-image` и увидим в логах последовательность `[GigaChat][slot-0] 402 → [GigaChat][slot-1] OK` при исчерпании токенов на первом ключе.
- Сценарий «у первого ключа кончились токены» больше не должен ломать ни поддержку, ни генерацию картинок.
