# План: E2E-проверка исправлений (не «по коду», а по факту)

Цель — пройти все 6 пунктов из «Перечня ошибок платформы СИНТАГМА» руками через браузер на синтагма.рф / sintagma.com.ru под реальной ролью владельца организации, поймать конкретные HTTP-ответы и убедиться, что:
- запросы возвращают 2xx,
- файлы реально загружаются и доступны по signed URL,
- видео проигрывается до конца, а не висит на спиннере,
- регистрация по ссылке реально создаёт пользователя,
- добавление ученика на курс не падает,
- протоколы аттестационной комиссии открываются и скачиваются.

Никаких изменений кода в этом плане нет — только верификация. Если по ходу всплывут регрессии, фиксы внесу отдельным планом.

## Что проверяю и как

### 1. Загрузка фото профиля (org owner и ученик)
- Зайти в кабинет организации → «Профиль» → загрузить .jpg, .png, .webp (≥1 МБ и ~3 МБ).
- Проверить через `browser--list_network_requests`: PUT/POST в `storage/v1/object/avatars/...` → 200.
- Перезагрузить страницу, убедиться, что аватар реально подтянулся (signed URL не 400/404).
- Повторить под учеником (другой роль), потому что bucket один — `avatars`.
- Логи: `supabase--analytics_query` по `storage` за последние 10 минут на 403/404/«Bucket not found».

### 2. Брендирование организации (логотип + обложка логина)
- В «Брендирование» загрузить логотип (PNG с прозрачностью) и фон логина (JPG 1920×1080, ~2–4 МБ).
- Сеть: PUT в `storage/v1/object/org-branding/<org_id>/...` → 200.
- Открыть страницу логина организации в инкогнито — обложка и логотип отображаются.
- Под не-владельцем (member без права `branding.manage`) убедиться, что INSERT в bucket даёт 403 (RLS работает).

### 3. Регистрация по ссылке `/join/:token`
- Сгенерировать ссылку приглашения, открыть в инкогнито.
- Зарегистрироваться новым email/паролем; повторить с заведомо невалидным паролем и уже существующим email — увидеть конкретный текст ошибки (не «Произошла ошибка»).
- Сеть: `auth/v1/signup` → 200 на валидных данных; в `JoinByLink.tsx` сообщение из `error.message` пробрасывается в UI.
- В БД: `select id, email, created_at from auth.users order by created_at desc limit 5` — пользователь появился и привязан к организации (`organization_members`).

### 4. Добавление ученика на курс (массово и поштучно)
- В «Студенты курса» добавить 1 ученика и пачку 20+.
- Сеть: RPC/insert в `course_enrollments` → 200. Проверить, что при искусственном сбое (DevTools throttling → Offline на 1 секунду) срабатывает retry 3× с backoff и финальный toast — человекочитаемый.
- `supabase--read_query`: `select count(*) from course_enrollments where created_at > now() - interval '10 min'` совпадает с ожиданием.

### 5. Видео в уроках (Kinescope для всех тарифов)
- Открыть курс с ≥10 видеоуроками под учеником.
- Проверить, что во ВСЕХ уроках плеер Kinescope инициализируется и видео играет (а не только в первом).
- Сеть: запросы к `kinescope.io` → 200; нет 401/403 от `KINESCOPE_API_TOKEN`.
- `subscriptionPlans.ts`: `kinescopeEnabled: true` во всех 5 тарифах — подтвердить, что в фиче-гейте плеер не блокируется на низких тарифах.
- Edge function logs `kinescope-*` за период теста — нет ошибок токена.

### 6. Протокол аттестационной комиссии — просмотр и скачивание
- Завершить тест ученика так, чтобы сгенерировался автопротокол.
- В «Документы → Протоколы аттестации» нажать «Просмотр» и «Скачать».
- Сеть: вызов `storage.from('org-documents').createSignedUrl(...)` → возвращает `signedUrl` (не null), последующий GET по URL → 200, `Content-Type: application/pdf` (или docx).
- Если файл отсутствует в bucket (legacy запись в БД без объекта) — убедиться, что toast говорит «Файл не найден в хранилище», а не молча ничего не делает.

## Технические инструменты для верификации
- `browser--navigate_to_url` + `browser--act` + `browser--list_network_requests` / `get_network_request_details` для каждого сценария.
- `supabase--analytics_query` (storage + auth logs) и `supabase--read_query` для подтверждения побочных эффектов.
- `supabase--edge_function_logs` для Kinescope и регистрации.
- `supabase--linter` в конце — на случай, если по дороге всплыли RLS-предупреждения.

## Что получит клиент
Короткий отчёт по 6 пунктам в формате:
```
1. Аватар  — OK (PUT 200, signed URL 200, проверено на jpg/png/webp)
2. Брендирование — OK / FAIL + причина
3. Регистрация по ссылке — OK / FAIL + текст ошибки
4. Добавление ученика — OK / FAIL + код
5. Видео в уроках — OK / FAIL по конкретному уроку
6. Протоколы — OK / FAIL
```
с указанием реальных request-id и временных меток, чтобы спор «исправлено / не исправлено» закрылся фактами.

## Доступы, которые нужны
Для шагов 1–6 нужен либо тестовый аккаунт владельца организации с уже подключённым тарифом и хотя бы одним курсом, либо разрешение зайти под учёткой клиента (ЧУДПО «Школа пожарной профилактики» или другая тестовая орг).
