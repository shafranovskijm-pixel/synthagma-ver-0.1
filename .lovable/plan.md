## Почему карточка открывается долго

В хуке `useOrgDetailsView` стоит один общий `setLoading(true)` и `Promise.all` из 8 запросов — пока **все** не завершатся, отрисовывается только спиннер. Среди них есть очень тяжёлые:

1. **`fetchUsage` (главный тормоз)** — сканирует Supabase Storage рекурсивно:
   - 6 org-бакетов (`org-documents`, `company-documents`, `org-branding`, `library-files`, `billing-documents`, `student-documents`)
   - + по 2 бакета на каждый курс (`course-files`, `presentations`)
   - + внешний бакет `course-videos` через edge-функцию `get-external-storage-config`
   - У организации с 30 курсами это легко **70–100+ list-запросов к Storage**, каждый c глубиной до 2 уровней. Для статистики storage эти данные не нужны мгновенно — есть готовое поле `usage.storage_bytes` в `organization_usage`.

2. **`fetchCourses` — классический N+1**: на каждый курс отдельно `count` уроков и `count` enrollments (`Promise.all` по курсам, но всё равно 2×N запросов).

3. **`fetchStudents`** грузит всех студентов + все enrollments, нужен только при открытии вкладки «Ученики» (а по умолчанию открыта она же — но всё равно блокирует и показ шапки/обложки/тарифа).

4. Ещё 5 мелких параллельных запросов держат общий лоадер, хотя каждый из них нужен только своей вкладке (документы, история использования, реквизиты, брендинг, pending-enrollments).

В итоге пока админ не дождётся самого медленного из 8 запросов — экран пустой со спиннером.

## План оптимизации

### 1. Прогрессивный рендер вместо общего спиннера

Убрать общий `loading`, показывать шапку/обложку/навигацию сразу. Каждая вкладка получает свой локальный лоадер. Так открытие визуально станет почти мгновенным.

### 2. Заменить сканирование Storage на готовое значение из БД

В `fetchUsage`:
- читать `storage_bytes` и `ai_generations_count` напрямую из `organization_usage` за текущий месяц (одним запросом);
- удалить весь блок с `scanPath` по 8 бакетам и вызовом `get-external-storage-config`;
- если значение в `organization_usage` устарело/отсутствует — показывать «—» и предложить кнопку «Пересчитать», которая вызовет существующую edge-функцию пересчёта (используется в `usage-metrics`).

Это убирает десятки сетевых запросов и устраняет основной источник задержки.

### 3. Убрать N+1 в `fetchCourses`

Переписать на один запрос с агрегатами: `courses` + вложенные `lessons(count)` и `enrollments(count)` через PostgREST relation count, либо одним RPC. Получится 1 запрос вместо `1 + 2×N`.

### 4. Lazy-загрузка по вкладкам

Перенести из общего `Promise.all` в момент активации вкладки:
- `fetchStudents` + `fetchPendingEnrollmentsCount` → при открытии «Ученики»
- `fetchUsageHistory` → при открытии «Обзор»
- `fetchCredentials` → при открытии «Настройки»
- `fetchBranding` оставить в первичной загрузке (нужен в шапке), но не блокировать им рендер

Использовать `useState` с флагом `loaded` для каждого блока и не перезапрашивать при переключении.

### 5. Кэш на уровне компонента списка

В `OrganizationsManager` при возврате к карточке ранее открытой организации переиспользовать данные из `sessionStorage` (TTL ~60 сек), чтобы повторное открытие было моментальным.

## Технические детали

- Файлы под изменение:
  - `src/hooks/useOrgDetailsView.ts` — разделить на отдельные `useEffect` по вкладкам, удалить storage-сканер, переписать `fetchCourses`.
  - `src/components/admin/OrganizationDetailsView.tsx` — убрать ранний return со спиннером, добавить локальные лоадеры в панелях.
  - `src/components/admin/org-details/OrgStatsPanel.tsx` — добавить кнопку «Пересчитать хранилище», которая вызывает существующий пересчёт через edge-функцию.
  - При необходимости — новая SQL-функция `get_org_courses_with_counts(org_id)` для агрегатов курсов.

- Не трогаем: RLS, схема таблиц, edge-функции пересчёта storage (используем существующие).

## Ожидаемый эффект

- Первый кадр карточки: **мгновенно** (вместо 3–10 сек).
- Сетевая нагрузка при открытии: ~3–4 запроса вместо 50–150.
- Переключение вкладок: данные грузятся только под активную вкладку.
