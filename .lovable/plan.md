
## Задача
Реализовать сквозной процесс подписания документов (договоры, согласия, акты) через простую электронную подпись (ПЭП) — связь админка ↔ организация ↔ ученик/контрагент. По 63-ФЗ и 152-ФЗ.

## Что уже есть
- **Согласия учеников** — `StudentConsentForm.tsx` уже содержит блок про ПЭП по 63-ФЗ (логин+пароль = ключ ЭП).
- **Договоры/акты с печатью и подписью организации** — `useContractGenerator.ts`, `useActGenerator.ts` (поля `signature_url`, `stamp_url` орг.).
- **Подписание PDF админом** — `admin/sales/DocumentSigning.tsx` (накладывает печать/подпись Шафрановского).
- **Таблицы**: `student_consents`, `org_contracts`, `org_billing_documents`, `consent_documents`.
- **Чего нет**: единого процесса «отправить документ на подписание получателю» + отдельного **Соглашения о ПЭП** между организацией и контрагентом/учеником.

## Юридическая база (по 63-ФЗ ст.6, 9 + 152-ФЗ)
Соглашение о ПЭП **обязательно** должно содержать:
1. Правила определения подписанта по ПЭП (login = email + пароль учётной записи).
2. Обязанность подписанта обеспечивать конфиденциальность ключа ЭП.
3. Признание сторонами равной юр. силы документов с ПЭП и собственноручной подписью.
4. Перечень видов документов, для которых применяется ПЭП.
5. Порядок проверки подписи (по логам входа: IP, user-agent, timestamp, hash документа).
6. Ограничения: ПЭП не применяется там, где закон требует КЭП.

## План реализации

### 1. Миграция БД — единая таблица процесса подписания
**Новая таблица** `document_signatures`:
- `id`, `document_type` ('contract' | 'consent' | 'pep_agreement' | 'act' | 'order' | 'custom_pdf')
- `document_id` (ссылка на org_contracts / student_consents / org_billing_documents)
- `organization_id`, `sender_user_id` (кто отправил)
- `recipient_type` ('student' | 'company' | 'individual'), `recipient_user_id`, `recipient_email`, `recipient_name`
- `status` ('draft' | 'sent' | 'viewed' | 'signed' | 'rejected' | 'expired')
- `document_html`, `document_hash` (SHA-256 для фиксации содержимого), `document_snapshot_url` (PDF в Storage)
- `signed_at`, `signed_ip`, `signed_user_agent`, `signature_token` (одноразовая ссылка для не-юзеров)
- `pep_agreement_id` (ссылка на принятое соглашение о ПЭП)
- `expires_at`, `created_at`
- RLS: org видит свои; получатель видит по `recipient_user_id` или по токену.

**Новая таблица** `pep_agreements` (Соглашение о ПЭП):
- `id`, `organization_id`, `user_id` (или `email` + `full_name` для гостей)
- `agreement_text`, `agreement_version`, `accepted_at`, `ip`, `user_agent`
- Уникальность: `(organization_id, user_id, agreement_version)`.

### 2. Шаблон Соглашения о ПЭП
**Файл:** `src/constants/pepAgreementTemplate.ts` — текст соглашения с переменными `{{org_name}}`, `{{org_inn}}`, `{{user_name}}`, `{{user_email}}`, со всеми пунктами по 63-ФЗ (см. выше). Плюс `getPepAgreementHtml()` для предпросмотра в стиле A4.

### 3. UI — кнопка «Отправить на подписание»
В местах, где уже есть документы:
- **Организация** → `DocumentsTab` (договоры, акты, приказы, согласия) — добавить меню «⋯» с пунктом «Отправить на подписание».
- **Ученик** → карточка ученика → новая вкладка/секция «Документы на подпись».
- **Админка** → `SalesContracts` → кнопка «Отправить контрагенту».

Открывается диалог `SendForSigningDialog`:
- Выбор получателя (ученик из списка / e-mail для внешних).
- Срок действия ссылки (по умолч. 7 дней).
- Превью документа.
- Кнопка «Отправить» → вставка в `document_signatures` со статусом `sent` + edge-функция `send-signing-email`.

### 4. Страница подписания
**Новый маршрут:** `/sign/:token` (доступен **без авторизации** — по signature_token; для зарегистрированных — авто-логин-привязка).

Шаги мастера:
1. **Подтверждение личности** (для гостей: ФИО + email-код через SMTP; для учеников — текущая сессия).
2. **Принятие Соглашения о ПЭП** (если ещё не принято в текущей версии) — отдельный шаг с прокруткой и чекбоксом → запись в `pep_agreements`.
3. **Просмотр документа** (iframe с HTML/PDF) + хеш SHA-256 виден.
4. **Подписание** — чекбокс «Я подписываю документ простой ЭП» → кнопка «Подписать» → запись в `document_signatures` (status='signed', ip, ua, signed_at).
5. **Готово** — кнопка «Скачать подписанный PDF».

### 5. Визуализация подписи на документе
- Если подписант — **организация**, у которой есть `stamp_url`/`signature_url` → штамп+факсимиле накладываются (используем существующую логику `useContractGenerator`).
- Если подписант — **физлицо/ученик** → плашка в стиле «Госуслуг»:
  ```
  ┌─────────────────────────────────────┐
  │  ✓ ДОКУМЕНТ ПОДПИСАН                │
  │  Простой электронной подписью       │
  │  ФИО: Иванов Иван Иванович          │
  │  Email: ivanov@mail.ru              │
  │  Дата: 18.04.2026 14:32 (МСК)       │
  │  IP: 178.xx.xx.xx                   │
  │  Соглашение ПЭП: №PEP-2026-001234   │
  │  Хеш документа: a3f5...e9b1         │
  └─────────────────────────────────────┘
  ```
  Компонент `<PepSignatureStamp />`, вставляется в HTML/PDF при экспорте.

### 6. Edge-функции
- `send-signing-email` — SMTP-письмо с ссылкой `/sign/:token` (через существующий шаблонный SMTP).
- `verify-signing-otp` — отправка/проверка OTP-кода для гостей.
- `finalize-signature` — серверная фиксация подписи: валидация токена, генерация PDF-snapshot с плашкой/печатью, запись хеша, сохранение в Storage `signed-documents`, статус `signed`.

### 7. Журнал подписаний
- В админке (Settings → новая вкладка «Подписания») и в орг-кабинете → таблица всех `document_signatures` с фильтрами (статус, тип, получатель, период).
- Просмотр: документ + блок «Доказательства подписи» (соглашение ПЭП, IP, UA, хеш, timestamp).

### 8. Что НЕ трогаем
- `useAuth.tsx`, роуты слушателей, RLS существующих таблиц — без изменений.
- `StudentConsentForm` — оставляем, только добавляем интеграцию с `pep_agreements` (один раз показываем соглашение о ПЭП).

## Этапы (для безопасного релиза)
1. **Этап 1** — миграция + шаблон ПЭП + страница `/sign/:token` (только для согласий учеников). Тест без рисков для входа.
2. **Этап 2** — расширение на договоры/акты, кнопка «Отправить на подписание» в орг-кабинете.
3. **Этап 3** — журнал подписаний в админке + экспорт PDF с доказательствами.

## Технические детали
- Хеш документа: `crypto.subtle.digest('SHA-256', ...)` на клиенте + сверка на сервере.
- Хранение PDF-snapshot: бакет `signed-documents` (новый, RLS: org + получатель).
- Токен подписания: `crypto.randomUUID()` + срок жизни.
- Письма: используем существующий SMTP-стек (Timeweb).
- Никаких изменений в auth — проверено по прошлой договорённости.
