
Проблема уже достаточно локализована: это не похоже на “секрет вообще не подставился”, потому что функция доходит до вызова API Яндекса и получает осмысленный `403 ApiRestrictedToOrganizations`. Если бы токена не было в рантайме, сработал бы ваш собственный ответ `TOKEN_NOT_CONFIGURED` из `telemost-create-conference`.

Что я проверил по коду:
- `supabase/functions/telemost-create-conference/index.ts` читает только `YANDEX_TELEMOST_OAUTH_TOKEN` и реально отправляет его в `Authorization: OAuth ...`.
- Логи функции показывают именно ответ Яндекса `403 ApiRestrictedToOrganizations`, а не ошибку отсутствия секрета.
- `manage-secret/index.ts` сейчас вообще не разрешает `YANDEX_TELEMOST_OAUTH_TOKEN` в whitelist, то есть через ваш встроенный UI такой секрет штатно не сохраняется.
- Вызов создания вебинара идёт из двух мест: `CreateWebinarDialog.tsx` и `WebinarsManager.tsx`.

План исправления:
1. Убрать двусмысленность с секретом
- Добавить `YANDEX_TELEMOST_OAUTH_TOKEN` в whitelist функции `manage-secret`.
- Если есть админский экран редактирования ключей, добавить этот ключ в список отображаемых секретов, чтобы его можно было обновлять из интерфейса.

2. Добавить безопасную диагностику в `telemost-create-conference`
- Не выводить токен целиком.
- Временно логировать только безопасный отпечаток токена:
  - длину,
  - первые/последние 4 символа,
  - hash/fingerprint.
- Это позволит точно понять, использует ли функция новый токен после обновления.

3. Зафиксировать поведение после смены секрета
- После обновления секрета обязательно переиспользовать/перезадеплоить функцию, чтобы исключить сценарий “секрет обновили, а рантайм ещё держит старое значение”.
- Повторно проверить вызов создания вебинара.

4. Развести два возможных исхода
- Если fingerprint в логах совпадёт с новым токеном, а Яндекс всё равно отвечает `ApiRestrictedToOrganizations`, значит проблема вне приложения: сам токен/аккаунт Яндекса не имеет фактического доступа к Telemost API для организации.
- Если fingerprint не совпадёт, значит секрет действительно не применился, и надо чинить поток сохранения/деплоя секрета.

5. Подправить UX, чтобы не было ощущения “просто выкинуло”
- Сохранить уже добаванную обработку ошибок без blank screen.
- Показать пользователю явное сообщение вида:
  - “Используется токен, но Яндекс отклонил его как неорганизационный”
  - или “Токен не применился после обновления”.

Технические детали:
- Файлы для изменения:
  - `supabase/functions/manage-secret/index.ts`
  - вероятно `src/components/admin/ai-settings/constants.ts` или связанный UI списка ключей
  - `supabase/functions/telemost-create-conference/index.ts`
- Почему это важно:
  - сейчас код умеет только “верить”, что секрет правильный;
  - после правки мы сможем доказать, используется ли новый токен на самом деле;
  - это снимет главный вопрос: “не вставили ли GVT/Telemost токен в секреты”.

Ожидаемый результат после реализации:
- либо вебинар начнёт создаваться;
- либо мы получим окончательное подтверждение, что новый токен реально используется, а отказ идёт уже со стороны Яндекса/организации, а не из-за кода или секрета.
