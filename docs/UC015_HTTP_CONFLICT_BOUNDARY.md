# UC015: HTTP conflict boundary (migration 616)

The public journal RPCs return SQLSTATE PT409 with the existing message CUSTOM_JOURNAL_REVISION_CONFLICT. PostgREST maps PT409 to HTTP 409. The client already recognizes this message; no layout or client error contract changes are needed.

Supabase documents that returning custom SQLSTATE 40001 from an RPC may cause repeated transactions even after a client disconnects: https://supabase.com/kb/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions . Correcting a function does not stop already running retrying backends. Existing sessions must be handled separately using their exact verified identity and query; this migration never terminates backends.

Only read_scoped_custom_journals(uuid,jsonb,jsonb) and apply_scoped_custom_journal_action(uuid,jsonb,bigint,uuid,jsonb) are changed. Their full former PL/pgSQL bodies remain byte-identical inside a new outer block. The outer serialization_failure handler is needed because both former bodies can raise 40001 from their own lock_not_available exception handler; a sibling handler cannot catch an exception raised inside that handler.

The migration guards the actual615 body MD5/SHA256, owner, security-definer flag, volatility, JSONB return type, language and complete search_path/TimeZone configuration. It replaces each body once through pg_get_functiondef. Before/after comparison preserves all public function metadata and ACL, all other public function bodies, public relation/column/policy/trigger metadata, role memberships, roles and default ACL. Private helpers retain their original error codes and privileges. No journal, learner, programme, attendance or outcome data are modified.

The separate rehearsal.sql is source only until executed by the release owner. It temporarily applies616, checks a healthy read, an actual stale save_schema call yielding PT409, unchanged invalid-input22023 and private-helper40001, and byte hashes of all rows for exactly the two named QA journals. It uses one of the two existing authorized QA staff identities as local SQL claims; it is explicitly a database protocol check, not proof of an Auth login. It ends in ROLLBACK and does not register a migration ledger row. Counts are observed and bounded, not preset expected results.

After a successful rollback rehearsal, verify both original615 body digests and unchanged ledger615. Publish and atomically register616 using the normal guarded release. Then verify the live HTTP response to a stale edit returns409 once, valid reads/saves still work, no new retrying QA backend remains, and earlier saved export byte hashes match. A separate two-session read-fence conflict should additionally confirm PT409 on the read RPC's former lock handler. Source inspection and a prepared rehearsal are not execution or deployment proof.
