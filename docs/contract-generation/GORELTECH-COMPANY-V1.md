# ГОРЭЛТЕХ: договор с компанией-заказчиком v1

Статус: `1.0.0-draft`. Техническая верность клиентскому источнику подтверждена постранично; юридическое согласование текста остаётся отдельным клиентским этапом.

## Почему текущая генерация не подходит

Текущий мастер `GenerateContractDialog.tsx` хранит договор как `body_html` и собирает DOCX через `htmlToDocxBlob`. Загрузка клиентского DOCX также переводит файл в HTML. Поэтому итоговый Word-файл не является заполненной копией клиентского документа: теряются исходные секции, разрывы страниц, таблицы, колонтитулы и приложения. `process-contract-template` дополнительно использует AI для изменения текста, что недопустимо для утверждённого юридического шаблона.

Для шаблонов формата `docx_ooxml` запрещено использовать цепочку DOCX → HTML → DOCX и запрещено отправлять юридический текст в AI для автоматической правки.

## Файлы-источники

- `docs/group-documents/client-templates/goreltech-group-package-v1/source/company_contract.source.doc` — точный клиентский файл из архива `для сайта (1).zip`; SHA-256 `D8B70377F773EAFF0A9C00BF018BA97CB5437E78DB9ACA9C1B91DCB1928DB965`.
- `_shared/contract-templates/goreltech/company/v1/template.docx` — DOCX-first рабочая копия клиентского Word-файла с токенами вместо заполняемых полей.
- `_shared/contract-templates/goreltech/company/v1/manifest.json` — 35 типизированных переменных, повторители, условные приложения и правила блокировки.
- `DOCX-FIRST-CONTRACT-ALGORITHM.md` — общий алгоритм адаптации договоров других клиентов.

Шаблон содержит 5 секций, 11 таблиц и базово рендерится в 12 страниц. Все 12 страниц сопоставлены с клиентским оригиналом 15.08.2026. Из клиентского источника удалены только жёлтая служебная подсветка и неиспользуемое вложение PDF с иконкой; заполняемые поля заменены типизированными токенами. Юридический текст, таблицы, разделы, разрывы страниц и подписи сохранены.

## Целевая архитектура

1. `org_contract_templates` хранит формат шаблона (`html` или `docx_ooxml`), сценарий, версию, статус, приватный storage path исходного DOCX, JSON-манифест и SHA-256.
2. Для `docx_ooxml` мастер собирает канонический снимок данных из организации, компании, группы, курса, слушателей и настроек оплаты.
3. Перед генерацией сервер валидирует снимок по `blocking_rules` манифеста. Нельзя создавать «почти заполненный» договор.
4. Серверная функция компилирует копию DOCX напрямую: заменяет скалярные токены, клонирует строки `programs[]` и `students[]`, включает только выбранные учебные планы и удаляет неиспользованные прототипы.
5. Итоговый DOCX загружается в приватный `billing-documents`. В `org_contracts` сохраняются исходный снимок, версия шаблона, SHA-256 результата, `docx_path`, `pdf_path`, статус и автор.
6. PDF и предпросмотр должны строиться только из уже заполненного DOCX отдельным сервисом рендера (LibreOffice/Word-compatible worker). Нельзя продолжать формировать PDF из отдельного HTML.
7. Если сервис DOCX→PDF ещё не подключён, интерфейс честно показывает `DOCX готов, PDF формируется/недоступен`; HTML-подмена не допускается.

## Пользовательский сценарий P0

В «Ученики → Группы → Документы группы → Договоры»:

1. Пользователь выбирает `Компания-заказчик`.
2. Система подставляет компанию, группу, курс, даты, форму, часы, стоимость и всех слушателей группы.
3. Экран «Готовность данных» показывает блоки: стороны и подписант; программа и группа; оплата и НДС; слушатели; приложения.
4. Ошибки показываются рядом с полем и одной сводкой. Кнопка `Сформировать договор` отключена при блокирующей ошибке.
5. После генерации открывается карточка результата: версия шаблона, дата/номер, контрагент, количество слушателей, статусы DOCX/PDF и действия `Просмотр`, `DOCX`, `PDF`, `Создать новую версию`.
6. Утверждённый или подписанный договор не перезаписывается.

## Обязательные данные

- номер и дата договора;
- компания, ИНН, КПП, ОГРН, юридический/почтовый адрес, банк, БИК, счета, email, телефон;
- ФИО подписанта в родительном падеже, должность, основание полномочий, краткое ФИО;
- группа, курс, название программы, форма, даты, место и расписание;
- сумма цифрами и вычисленная сумма прописью;
- явно выбранные формулировки НДС и графика оплаты;
- минимум одна программа и один слушатель;
- для каждого слушателя: ФИО, образование, контакты, должность, программа и даты.

Отсутствие адреса проживания слушателя допускается манифестом, но интерфейс показывает предупреждение. Данные ФРДО переиспользуются для проверки ФИО, образования и документов, но договор и запись ФРДО остаются отдельными сущностями.

## Два юридических сценария

`Компания-заказчик` и `Физическое лицо` — разные семейства шаблонов. Нельзя получать физлицо условным скрытием абзацев в этом DOCX. Пока клиент не согласовал отдельный текст для физлица, существующий сценарий физлица остаётся отдельным и не помечается как соответствующий шаблону ГОРЭЛТЕХ.

## Состояния и версии

- `draft` — создан, допускает изменение входных данных с созданием новой версии;
- `validated` — все проверки пройдены;
- `approved` — согласован, неизменяем;
- `signed` — подписан, неизменяем;
- `cancelled` — отменён с причиной.

Каждая новая генерация сохраняет `template_id`, `template_version`, `template_sha256`, `variables_snapshot`, `result_sha256`, автора и время. Старые договоры не меняются при обновлении шаблона.

## Этапы реализации

### P0.1 — модель и компилятор DOCX

- миграция полей шаблона/договора;
- регистрация bundled-шаблона ГОРЭЛТЕХ как `docx_ooxml`, `legal`, `1.0.0-draft`;
- авторизованная server-side компиляция DOCX;
- блокирующая валидация и журнал результата;
- тесты токенов, повторителей, условных учебных планов и приватного storage.

### P0.2 — мастер и карточка готовности

- переключение мастера по `template_format`;
- экран готовности данных;
- генерация одной компанией для всех выбранных слушателей;
- version/status UI и сохранение результата;
- интеграционные тесты individual/legal без смешивания.

### P0.3 — единый PDF/preview

- очередь рендера заполненного DOCX;
- приватный PDF, статусы и повтор;
- `Просмотр` использует именно сохранённый PDF;
- сверка номера, даты, суммы, слушателей и количества страниц между DOCX/PDF.

## Приёмка

- исходный DOCX никогда не проходит через Mammoth/HTML;
- все 35 токенов разрешены, в результате нет `[[...]]`;
- приложение №1 содержит точное число выбранных слушателей;
- программа, количество слушателей, номер и дата совпадают во всех местах;
- сумма цифрами совпадает с суммой прописью, НДС выбран явно;
- включены только учебные планы выбранных курсов;
- результат переживает перезагрузку страницы и открывается из списка договоров;
- private storage не становится публичным;
- тесты: короткие значения, длинные реквизиты, несколько программ, максимальная группа, missing field, повторная версия, individual/legal isolation;
- DOCX и PDF проходят постраничную визуальную проверку без обрезки таблиц и подписей.
