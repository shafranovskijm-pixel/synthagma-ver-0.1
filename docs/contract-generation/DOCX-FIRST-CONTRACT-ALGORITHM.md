# Алгоритм адаптации клиентских договоров

## Принцип

Оригинальный DOCX клиента является источником юридического текста и оформления. Система не преобразует его в HTML и не собирает новый Word-файл «с нуля». Для каждого шаблона хранятся:

1. неизменённый исходный DOCX;
2. машинный манифест переменных, циклов и условий;
3. версия шаблона и контрольная сумма;
4. проверочный набор данных;
5. эталонный рендер и протокол приёмки.

## Шаг 1. Приём исходника

- Принимать DOCX. Legacy DOC конвертировать в рабочую копию, не меняя исходный файл.
- Зафиксировать SHA-256, автора версии, дату получения и назначение договора.
- Определить сценарий: компания, физлицо, трёхсторонний договор или смешанный пакет.
- Отдельно получить подтверждение юридического текста для каждого сценария.

## Шаг 2. Полная инвентаризация

- Отрендерить и проверить все страницы.
- Зафиксировать секции, поля, колонтитулы, стили, таблицы, приложения и подписи.
- Выделить неизменяемый юридический текст, скалярные поля, повторяемые таблицы и условные разделы.
- Найти одинаковые значения, которые должны заполняться из одного источника: номер/дата договора, подписант, программа, стоимость.

## Шаг 3. Каноническая модель данных

- Организация-исполнитель.
- Компания или физлицо-заказчик.
- Подписант и основание полномочий.
- Группа, курс, даты, место, форма и расписание.
- Стоимость, налоговый режим и график оплаты.
- `students[]` и `programs[]`.
- `curricula[]` как условные приложения.
- Вычисляемые значения: суммы прописью, склонения ФИО, краткие ФИО и даты словами.

Каждое поле получает тип, источник, обязательность, формат, правила проверки и допустимость ручного переопределения.

## Шаг 4. Манифест

- Связать канонические ключи со стабильными местами в DOCX.
- Не использовать текст абзаца как единственный локатор.
- Для таблиц хранить индекс таблицы, число заголовочных строк и строку-прототип.
- Для приложений хранить условие включения и код программы.
- Для налогов и оплаты использовать готовые согласованные пункты, а не склейку случайных фрагментов.

## Шаг 5. Компиляция

1. Проверить SHA-256 исходного шаблона.
2. Создать копию шаблона.
3. Проверить все блокирующие данные.
4. Заполнить скалярные поля непосредственно в OOXML.
5. Клонировать строки программ и слушателей из строк-прототипов.
6. Включить только нужные учебные планы.
7. Удалить незадействованные строки и маркеры.
8. Сохранить снимок входных данных, версии шаблона и итогового DOCX.

## Шаг 6. Контроль качества

- Проверить отсутствие незаполненных токенов.
- Сверить суммы, даты, количество слушателей и программы между всеми приложениями.
- Отрендерить итоговый DOCX и проверить каждую страницу.
- PDF создавать из уже заполненного DOCX.
- Предпросмотр также строить из того же снимка, а не из отдельного HTML-шаблона.
- Сравнить DOCX, PDF и предпросмотр по содержанию и пагинации.

## Шаг 7. Выпуск и изменения

- Состояния: черновик, проверен, утверждён, подписан, отменён.
- После утверждения документ неизменяем; исправление создаёт новую версию.
- Хранить автора, время, причину изменения и отличия версий.
- Изменение шаблона не должно менять уже выпущенные договоры.

## Критерий готовности нового клиентского шаблона

Шаблон считается готовым только после генерации минимум трёх наборов: короткие значения, длинные реквизиты и максимальная группа. Все варианты должны пройти проверку DOCX/PDF без обрезки, потери таблиц, пустых обязательных полей и расхождений между приложениями.
