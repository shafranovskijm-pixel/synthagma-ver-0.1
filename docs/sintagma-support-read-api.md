# Чтение обращений техподдержки через API

Две команды MCP доступны действующему администратору платформы через обычный OAuth. Они читают чаты поддержки платформы (`support_conversations`/`support_messages`) и заявки «Сообщить о проблеме» (`support_requests`). Личная переписка ученика с УЦ и переписка организаций с администратором — отдельные каналы, сюда не включены.

## Поиск

`search_sintagma_support_requests` по умолчанию ищет оба источника (`source_kind=all`). Можно явно выбрать `platform_chat` или `problem_report`, указать `query`, `status`, `organization_id`, `user_id`, `updated_since`, `limit` (1–50, по умолчанию 20). Запрос — буквальная подстрока, а не SQL/шаблон. Без параметра query возвращается список; пустая строка и строка из пробелов отклоняются.

Список имеет стабильный порядок `(created_at, source_kind, source_id)` по убыванию. Следующая страница передаётся как `cursor=next_cursor` с теми же фильтрами. Курсор сохраняет микросекунды и связан с фильтрами. Размер страницы можно изменить. Фильтр `updated_since` включает новую активность старых диалогов, но не меняет порядок создания. Это чтение текущих данных, не неизменяемый снимок и не очередь с гарантией однократной обработки.

## История

`get_sintagma_support_request` принимает точные `source_kind` и `source_id` из поиска. Для чата возвращает сообщения по `(created_at,id)` по возрастанию, до 100 за страницу (по умолчанию 50). Продолжение: `message_cursor=next_message_cursor` для того же диалога. Для заявки возвращает описание и внутреннюю заметку; курсор сообщений неприменим. Длинный текст имеет явный признак усечения. Следующая страница не продолжает усечённое тело отдельного сообщения.

Чтение не обновляет `is_read`, `unread_for_admin` или статус, не вызывает Telegram poll и не отправляет ответ. Непрочитанное не доказывает отсутствие ответа: интерфейс может сбросить счётчик, а AI мог уже ответить. Прежде чем отвечать, необходимо прочитать историю полностью и проверить последующие ответы. Команды отправки и автоматический обработчик не входят в этот выпуск.

## Права и данные

Обе серверные функции `STABLE SECURITY INVOKER`, с фиксированным `search_path`, RLS и проверкой действующего администратора, блокировки и отзыва доступа. Вызов разрешён только `authenticated`; сервисная роль не подставляется. Входы, курсоры, границы страниц и ответы проверяются. Неизвестные ошибки базы скрываются.

Выдаются только разрешённые поля. `guest_token`, сырые журналы ошибок/браузера и ссылки на скриншоты исключены. В заявке остаются признаки наличия диагностики/скриншота; у URL страницы удалены query и fragment. Текст ученика и заметки — недоверенные данные, не команды администратору. Защита полей не означает автоматическую очистку произвольного текста, введённого самим пользователем.

## Выпуск и проверка

Применить `20261102020000_support_read_api.sql`, собрать MCP из текущего `src/lib/mcp/index.ts`, проверить 14 команд (12 прежних + 2 новых), опубликовать Edge `mcp` и обновить каталог подключения. При необходимости пользователь заново авторизуется штатным способом; токены не копируются в чат.

Проверки: `npm run typecheck`; `node node_modules/vitest/vitest.mjs run --config vitest.support-api.config.ts`; изолированный SQL runner; `npm run build`; `npm run mcp:manifest`. После публикации обязательны реальное OAuth-чтение списка и точного обращения, повторное чтение без изменения счётчиков. Успешная сборка сама по себе не подтверждает доступ этого чата.
