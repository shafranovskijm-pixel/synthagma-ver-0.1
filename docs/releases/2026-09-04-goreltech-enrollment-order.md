# ГОРЭЛТЕХ: отдельный приказ о зачислении

Статус: локальная реализация, не подтверждённый production-релиз.
Основа изменения: `dfa8feeae5756bca3dca89a8a7632e31a11f3cc0`.

## Назначение и границы

В документах группы ГОРЭЛТЕХ добавлена отдельная карточка «Приказ о зачислении»
с пометкой Beta. Приказ относится к началу обучения: нужны организация, курс,
согласованные часы, период, состав и зачисление каждого участника. Будущие
итоговые оценки, удостоверения, ФРДО и закрытие журнала не требуются.

Исходный `enrollment_order` DOCX не изменён. После заполнения сохраняются
остальные ZIP-части, секция, шапка, исходные формулировки и пустое основание для
ручного заполнения. Наличие заполненного Word не является электронной подписью,
юридической проверкой полномочий или фактом выдачи образовательного документа.
Статус: **«Оформлен, готов к подписи»**.

Существующий пакет из девяти черновиков, его подтверждение подписантов и
ограничения сохранены. Интерфейс ученика, обучение, исходные шаблоны и старые
документы не изменены. Другие организации не получают карточку ГОРЭЛТЕХ.

## Реальный путь пользователя после развёртывания

1. Документы группы → «Оформить отдельный приказ».
2. «Проверить состав и реквизиты»: только чтение. Канонические программа, часы,
   даты и список совпадают с источниками будущего Word, включая fallback курса.
3. Самостоятельно указать дату, должность и ФИО подписанта; подтвердить данные.
   Дата и подписант не подставляются и не подтверждаются за пользователя.
4. «Оформить приказ и закрепить номер»: сервер заново сверяет снимок, фиксирует
   неизменяемые данные и один номер операции, собирает Word и подтверждает файл.
5. Скачать из «Оформленные приказы». Архив доступен отдельно от оформления,
   в том числе сотруднику с правом чтения, без доступа к изменению документов.

При потерянном ответе UUID сохраняется локально, без ФИО и других данных.
«Проверить состояние приказа» восстанавливает результат. Если сохранён только
номер, можно завершить тот же приказ. Если сервер пока не нашёл запись, можно
перечитать состав, подтвердить данные и явно повторить **с тем же UUID**.
Поздний первый запрос и повтор не должны создавать новый номер или менять уже
замороженные сведения. `null` не означает отмену и не освобождает UUID.
Web Locks не ставят второе оформление в очередь; версия локального индекса и
события другой вкладки сбрасывают устаревшее подтверждение.

## Серверный контракт

- Новый Edge: `issue-group-enrollment-order`, revision
  `goreltech-enrollment-order-v1`; действия preview/finalize/resume/status/list/download.
- Actor берётся из `auth.getUser()`, не из тела запроса.
- Новая аддитивная миграция: `20260904180000_goreltech_enrollment_orders.sql`.
- Таблица и служебные функции закрыты от прямых клиентских записей. RPC доступны
  только service-role с отдельной проверкой фактического actor и организации.
- Точный клиент проверяется по UUID, ИНН и имени; проверяется срок доступа staff.
  Чтение общего архива отделено от изменения своей операции.
- Снимок формируется одним SQL statement; номер `group_order` выделяется в той
  же транзакции после проверок. Ошибка откатывает резервирование.
- Новый private bucket `goreltech-issued-documents`. Ограничительные политики
  запрещают клиентам изменять его даже при старых permissive storage policies.
  Старый billing bucket не изменяется.
- Файл имеет путь organization/group/operation/SHA256. Upload без overwrite;
  восстановление проверяет существующие байты. Подтверждение связано с ledger.
- Нет cascading FK, который удалил бы исторический приказ вместе с группой.
  Скачивание: короткоживущая signed URL через существующий Nginx asset proxy.

  same-ID replay, архив после удаления группы, generic storage policies,
  XML/Unicode/trim-паритет и границы подписанта. SHA256 настоящий PostgreSQL,
  но production pgcrypto этим не проверен.
- Edge/helper: 50 тестов PASS; Deno check PASS.
- Клиент: 24 теста PASS; карточка: 16 тестов PASS.
- Существующий пакет после подключения карточки: 30 тестов PASS.

  предупреждения `no-explicit-any` в `GroupDocumentsFolder.tsx`.
- Actual SQL → Edge → DOCX: 46 проверок PASS на синтетическом RPC-экспорте;
  21 остальные ZIP-части оригинала неизменны. Это не фактический upload в Live.
- Синтетический Word:
  `D:/CodexTmp/goreltech-enrollment-sql-edge-20260904/sql-reserved-enrollment-order.docx`.
  SHA256 `2D934CD422B2A7343DCC0D1B5C2620D27709892EF172538EAA953EDAC1178531`.

ГОРЭЛТЕХ и официальный XML Минтруда этим изменением не объявляются готовыми.

## Релизный порядок и обратимость

1. Не повторять ранее отклонённые операции backup/экспорта и подтверждения
   подписантов без отдельного необходимого разрешения. Сначала разрешённая
   резервная копия и проверка наличия `extensions.digest(text,text)` и схемы.
2. На разрешённом тестовом окружении применить новую миграцию, развернуть Edge,
   проверить права/снимок/создание/повтор/скачивание на явно тестовых данных.
3. После подтверждённых локальных gates проверить точный Git SHA/Lovable sync
   и успешный platform preview; затем отдельно выпускать backend и frontend.
   Preview проекта с общей Live-базой не является изолированным staging.
4. Проверить через Nginx на синтагма.рф: номер, состав, Word после перезагрузки,
   повтор без нового номера, read-only архив, отсутствие регрессии старого пакета.
5. При откате интерфейса/Edge не удалять новый ledger, private файлы и номера.
   Возврат на предыдущую проверенную версию скрывает новый путь, но сохраняет
   историю. SQL rollback через удаление оформленных данных недопустим.

Не применялись Live DDL, Edge deploy, Publish, подпись или отправка клиенту.
