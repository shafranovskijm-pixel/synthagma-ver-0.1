# ГОРЭЛТЕХ: что отделяет пакет Word от окончательного оформления

Обновлено по коду `11ec9de6c2642e71e3fba42a3f5fd06263cdafb2` (Edge v20),
без запросов к данным production и без изменения клиентских шаблонов.
Наличие источника в коде не доказывает заполненность реальной группы.

## Текущее ограничение

Пакет из 9 DOCX собирается, но намеренно сохраняется как `draft`, без официальных
номеров. Это не полная готовность для окончательного оформления.

- `GroupDocumentsFolder.tsx` запрашивает для ГОРЭЛТЕХ черновик и не резервирует номера.
- `compile-group-class-journal/index.ts` передаёт `serverVerifiedCriticalRequisites: false`.
- Миграция `20260902141149_f6ca4d7b-d95c-4a00-ad7c-b29e85b40e46.sql` запрещает
  обойти это ограничение через браузерный или service-role batch RPC.
- `generation_status: generated` подтверждает сборку DOCX, а не проверку фактов.

## Карта источников и стадий

Восемь документов теперь имеют серверные builders, журнал использует сохранённые
ручные отметки. Прежнее описание, будто строки всё ещё берутся из browser HTML,
устарело. Ограничение окончательного оформления при этом остаётся.

| Документ / стадия | Реализованный источник | Что ещё нужно для окончательного оформления |
| --- | --- | --- |
| Приказ о зачислении / начало | Организация, группа, курс, часы, период, состав и точные enrollment IDs | Подтверждённые дата и подписант, неизменяемый состав, номер той же операции; выпускные результаты не нужны |
| Список обучающихся / начало | `profiles` и scoped `student_frdo_data` | Проверка отсутствующих/спорных полей именно для списка, без блокировки зачисления |
| Титульный лист / начало | Реквизиты, период, город из однозначного адреса | Дата оформления и подтверждение города при неоднозначности; не возвращать удалённый счётчик обучающихся |
| Расписание / начало | `group_document_schedules`, четыре блока, версия и автор | Подтверждение расписания; не обрезать дополнительные занятия и не подменять их онлайн-уроками |
| Журнал / обучение | Состав, четыре даты, scoped `group_class_journal_marks` | Раздельные открытие и закрытие журнала; будущие отметки остаются пустыми, прогресс не равен посещаемости |
| Пропуск / начало | Контакты, компании и даты группы | Подтверждённое основание пропуска; будущая посещаемость не препятствует подготовке |
| Ведомость аттестации / выпуск | Точный итоговый тест, реальные попытки, процент, enrollment IDs | Сохранённый итог аттестации и подтверждённая политика оценки/попытки; возможен ручной итог уполномоченного сотрудника |
| Приказ об отчислении / выпуск | Состав, период и сведения о завершении курса | Решение по каждому участнику, дата, номер и подписант; `completed` сам по себе не доказывает аттестацию |
| Книга регистрации / выдача | Реальные `education_document_records` и scoped личные данные | Подтверждённое событие выдачи и историческая связь записи; подписи не проставляются автоматически |

При явно подтверждённом обучении без выдачи удостоверений книга выдачи не должна
блокировать остальные документы: допускается рабочий бланк или применимое к данному
сценарию обозначение. Однако ни отсутствие записей, ни `expulsionOutcomeFallback`
не доказывают, что конкретная группа обучается без выдачи. Это нельзя выбирать за клиента.

`program_training_plans` связан с курсом, но наличие учебного плана не доказывает
утверждение образовательной программы. Нужны привязка документа и подсказки по
конкретным документам, а не глобальная блокировка обучения или обещание автоутверждения.

## Порядок завершения

Локально добавлен отдельный сценарий приказа о зачислении: серверный снимок,
явное подтверждение, один номер, неизменяемый Word и восстановление операции.
См. [реализацию и проверенные границы](2026-09-04-goreltech-enrollment-order.md).
Он ещё не принят визуально и не проверен на production; пункты ниже описывают
критерии завершения, а не утверждение готовности всех девяти документов.

1. Завершить отдельное действие **«Оформить приказ о зачислении»**, не связывая его
   с готовностью выпускной ведомости, удостоверений, книги выдачи и ФРДО.
2. Показать серверный состав и реквизиты; явно подтвердить дату приказа и подписанта.
   Зафиксировать неизменяемый снимок и номер под одним идентификатором операции.
   Повтор возвращает тот же номер и результат, а не создаёт новый приказ.
3. Заполнить исходный DOCX из зафиксированного снимка и сохранить оформленную версию
   с подтверждением операции. Старые оформленные файлы не перезаписывать.
   Статус **«Оформлен, готов к подписи»** не означает «подписан» или «выдан».
   Существующий девятидокументный draft RPC и его защиты не ослаблять.
4. Последовательно добавить оформление остальных документов по их стадии и
   собственным источникам. Ручные данные, автор и версия сохраняются явно.
   Наличие программы или будущих выпускных данных не превращать в общий запрет.
5. На тестовой группе ГОРЭЛТЕХ: сохранение → перезагрузка → скачивание всех
   девяти файлов → визуальная сверка с оригинальными DOCX и согласованными правками.
   Отдельно проверить заголовки, дословные формулировки, подписи и ориентацию страниц.

Это следующая работа по основной цели, не замена её требованием «черновик собрался».
Исходные шаблоны и рабочий интерфейс ученика сохраняются.

## Не создавать лишние блокировки

Готовность определяется для конкретного документа и стадии работы, не одним
требованием заполнить всё сразу. Отсутствие итоговых оценок или ещё не выданного
удостоверения не должно блокировать создание курса, зачисление и подготовку
документов начала обучения. Пустые поля, прямо предусмотренные оригинальным
шаблоном для ручного заполнения, не заменять выдуманными значениями и не считать
автоматически ошибкой источника. Неизвестный результат нельзя превращать в «сдал».
В одном пакете могут быть документы разной готовности; интерфейс должен объяснять
конкретное ограничение каждого, сохраняя доступ к уже рабочим операциям.
