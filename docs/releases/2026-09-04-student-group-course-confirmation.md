# Создание ученика с группой и подтверждённым курсом

04.09.2026. Кандидат поверх `2efbd779a`; продакшен этим документом не подтверждается.

## Пользовательский сценарий

1. Организация открывает «Ученики → Добавить ученика» и выбирает группу.
2. Если у группы есть курс, форма показывает его отдельно как «Курс группы». Он уже включён; повторно выбирать его не нужно. Другие курсы остаются доступны ниже.
3. После создания сервер и клиент проверяют сохранённую группу и её курс. Сообщение об успехе не заменяет фактическое чтение зачисления.
4. Если доступ к курсу истёк или запись не подтверждена, выводится частичный результат. Нужно открыть уже существующую карточку и проверить доступ, а не создавать дубликат ученика.
5. У группы без курса назначение группы не выдаётся за зачисление на обучение; форма прямо объясняет, что курс ещё не привязан.

## Исправления

- `register-student` revision `enrollment-persistence-v5`: после claim повторно читает профиль, группу и принадлежность её курса организации. Проверяет уникальный набор «курс группы + отдельно выбранный курс».
- Ранее существовавшее зачисление проверяется по user/course/id и сроку доступа. Существующие прогресс, даты и результаты не перезаписываются; `completed` остаётся доступным по текущему правилу даже после даты истечения.
- Ошибка после записи профиля возвращает структурированный `partial_success`, в том числе для существующего ученика с выбранной группой. Новые поля `group_confirmed`, `group_course_id`, `group_enrollment_confirmed`; `profile_persisted` отражает результат чтения (true/false/null). Нет автоматического повтора после потерянного ответа.
- Клиент независимо читает профиль → текущую группу → её курс → точное зачисление, поэтому не доверяет одному флагу успеха и работает с прежними ответами Edge без новых полей.
- Единый справочник групп включает course_id. Из формы удалена неверная подсказка «зачисление на курсы отдельно»; не теряются вручную выбранные дополнительные курсы при переключении группы.
- Миграция `20260904200000_group_registration_tenant_integrity.sql`: составные ссылки группа/курс/организация и профиль/группа/организация, проверка и блокировка связанных строк в триггерах. Квота, тело service-role RPC и его права не переписываются.
- Исправлена найденная независимым аудитом регрессия первого варианта миграции: обычное сохранение с неизменной группой/курсом НЕ восстанавливает намеренно удалённое зачисление. Проверка принадлежности всё равно выполняется.

## Ограничения и порядок выпуска

- PGlite использует одну сессию: реальные параллельные регистрации/изменения группы на PostgreSQL ещё не проверены. Блокировки и составные FK не выдаются за проведённый concurrency E2E.
- FK добавлены как NOT VALID: исторические нарушения не переписываются и не объявляются устранёнными. Отдельно требуется проверка исторических связей перед VALIDATE CONSTRAINT. Старые одно-колоночные FK сохраняются для прежних каскадов.
- При будущих неоднозначных PostgREST embeddings этих пар нужен явный FK hint. В текущем коде таких конфликтующих запросов аудит не обнаружил.
- Перед применением нужны согласованная резервная копия/проверка восстановления, версия PostgreSQL и проверка миграции на staging. Новые индексы/ALTER TABLE требуют оценки блокировок на реальном объёме данных.
- Далее отдельно: миграция → Edge v5 → frontend → проверка версии через Nginx и UI после перезагрузки. Nginx-шаблон с открытием revision header подготовлен в предыдущем коммите, его серверное применение не подтверждено.
- На реальном домене нужно пройти: новый ученик с группой; существующий ученик; группа без курса; одинаковый/разный дополнительный курс; сохранение настроек отчисленной группы; истёкший и завершённый курс; обновление страницы и вход ученика. В тестах использованы синтетические данные, а не учётные записи клиентов.
- Интерфейс ученика, исходные документы ГОРЭЛТЕХ и XML в этом пакете не менялись. Полная цель СИНТАГМЫ остаётся активной.
