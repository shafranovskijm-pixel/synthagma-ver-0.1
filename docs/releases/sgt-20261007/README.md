# Запрос Яны от 6 октября: архив и результаты ученика

Источник: Gmail `1a10fe97a44a5dc1`, письмо Яны Потаповой (СГТ). Импорт подтверждён клиентом; новые замечания относятся к удалению из архива и просмотру результатов в карточке ученика.

## Изменение поведения

Ранее «Удалить» в архиве повторно записывало `profiles.archived_at`. Запись оставалась в архиве, хотя интерфейс показывал «удалён». Теперь активный ученик по-прежнему переносится в архив, а удаление из архива требует подтверждения и устанавливает отдельный маркер `student_roster_removals(organization_id,user_id)` через RPC. Обновление списков/счётчиков происходит только после подтверждённого ответа сервера. Доступны одиночное и групповое удаление; одиночное действие можно отменить кнопкой «Вернуть в архив» в уведомлении.

Удаление не стирает профиль, зачисления, попытки, очные зачёты, документы и события тарификации. История другого учебного центра не затрагивается. Для последующего восстановления оператор может вызвать `set_archived_student_removed(org_id,user_id,false)` с правами владельца/администратора/сотрудника `students.write`. Восстановление возвращает ученика именно в архив.

В карточке добавлена вкладка «Результаты обучения»: все курсы ученика, прогресс, даты завершения, последние результаты каждого теста, число попыток и очные зачёты. Обычная история всех попыток остаётся во вкладке «Тестирование». Новая сводка загружает только выбранного ученика. Пустой результат отличается от ошибки; смена ученика не допускает отображения запоздалого ответа предыдущей карточки.

1. Сохранить `pg_get_functiondef` и ACL восьми RPC до изменений. Ожидаемый live preflight и резервные определения находятся у выпускающего агента в `D:/Codex/work/sintagma-queue/work/sgt-archive-results-20261007/production/`. Убедиться, что нет параллельного изменения этих функций.
2. Одной транзакцией применить `20261007100000_student_archive_removal.sql` и `20261007101000_student_learning_results.sql`. Первая миграция сохраняет текущие определения функций и добавляет только фильтр маркеров. При неизвестном предикате транзакция падает, а не заменяет функцию старой версией.
3. Подтвердить две новые RPC, RLS/отсутствие прямых клиентских INSERT/UPDATE/DELETE для маркера, фильтр во всех восьми RPC. При первом выпуске таблица маркеров должна быть пустой: миграция сама никого не удаляет.
4. Опубликовать фронтенд только после успешного шага 3. Существующие Edge Functions и секреты не меняются.
5. На технической QA-организации проверить карточку результатов и оба состояния архива. Для испытания удаления использовать только специально созданного/разрешённого QA-ученика. Записать ID, начальные значения, серверный результат, обновлённые счётчики, сохранённые попытки/документы; восстановить в первоначальное состояние. Учеников клиентов не удалять.
6. Проверить реальный домен после перезагрузки. Отчёт клиенту отделяет выпуск от её приёмки.

## Откат

Фронтенд можно вернуть на предыдущий релиз. До фактических операций удаления маркеров нет; восстановить восемь сохранённых определений RPC, удалить две новые RPC и пустую таблицу отдельной проверенной транзакцией. История обучения и тарификация не требуют восстановления: миграции их не изменяют.
