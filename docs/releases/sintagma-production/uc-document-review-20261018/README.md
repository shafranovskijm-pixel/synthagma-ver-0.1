# UC010 — внутреннее согласование конкретной версии

Пакет добавляет внутренний цикл проверки документа организации. Это запись решения внутри центра; она не создаёт ПЭП, электронную подпись, выданный образовательный документ, внешний регистрационный номер или сообщение. Старые документы, файлы, версии и утверждения не реконструируются.

Согласование относится к точному org_documents.current_version_id. Допускаются только версии upload/restore, связанные через storage_object_id с существующим объектом org-documents, точным путём org/versions/document/request.ext и сохранёнными size/etag/mimetype. Existing102 запрещает overwrite/delete такого объекта ещё со staging. Это проверка SQL-связи и метаданных, а не скачивание и криптографический хеш байтов.

Исторический URL без доказанной связи получает состояние unconfirmed: чтение и история сохраняются, изменения цикла запрещены. Пользователь может загрузить новую версию штатным UC006 интерфейсом. Новая или восстановленная версия получает отдельный цикл; прежнее решение к ней автоматически не переносится.

## Полномочия и переходы

Конфигурация требует действующего documents.write на всю организацию. Ответственный и согласующий — существующие активные owner/staff с таким правом. Назначение учебной группы не даёт преподавателю доступ к согласованию документов всей организации. Платформенный viewer не получает запись.

- Ответственный отправляет черновик на проверку.
- Назначенный согласующий запрашивает изменения, разрешает замечания и утверждает только состояние in_review.
- Ответственный и согласующий могут оставлять замечания. can_decide означает право разрешить замечание; готовность к утверждению проверяется отдельно.
- Нерешённые замечания блокируют утверждение. Принятые предложения вставки/удаления/замены требуют нового файла и нового цикла; HTML и байты автоматически не меняются.
- Закрытые циклы, исходный текст замечаний и решения по ним неизменяемы. Владелец организации может отменить открытый цикл; чужой writer не подменяет согласующего.

Один человек может быть назначен ответственным и согласующим: обязательное разделение этих ролей этим пакетом не устанавливается. Номер и дата внутреннего утверждения вводятся явно; дата/автор записи решения определяются сервером.

## RPC и история

get_org_document_workflow(document_id) возвращает текущий цикл, все прошлые циклы, точную текущую версию и capabilities. Имена участников сохраняются как снимки. Читателю истории не нужен доступ к общему списку сотрудников.

list_org_document_review_candidates(document_id) доступен только конфигурирующему writer. Связи ограничены конкретными курсами, группами и документами той же организации; они не расширяют ACL. Программные факты и утверждение образовательной программы относятся к UC011.

Записи выполняются через save_org_document_review_draft, transition_org_document_review, add_org_document_review_comment и resolve_org_document_review_comment. Они возвращают workflow snapshot. Прямые изменения четырёх новых таблиц закрыты для anon/authenticated/service_role; request receipts приватны.

40001 требует перечитать текущую версию; 42501 означает отсутствие действующих полномочий; 55000 — состояние/файл не позволяет действие; 22023 — неверные параметры или повтор UUID с другим телом. При неизвестном исходе запроса повторяется исходный UUID и полное исходное тело. Receipt возвращается только тому же действующему актёру после повторной проверки доступа.

Порядок блокировок: request advisory lock → документ → цикл. Точная версия и document/workflow CAS проверяются после блокировки. Поздняя ошибка события или receipt откатывает весь запрос.

## Порядок выпуска

1. Выполнить read-only preflight.sql. Требуются exact-source ledger100–109, полный postcheck предыдущего выпуска, неизменённые auth functions и append-only Storage policies.
2. Передать весь release-transaction.sql одним запросом. Это одна REPEATABLE READ транзакция с общим release lock и блокировкой ledger.
3. Получить все true из postcheck.sql. Wrapper сравнивает count+rowhash 51 существующей таблицы, все прежние policies/functions(owner/ACL тоже) и cron. Ни одна прежняя функция не заменяется; четыре новые таблицы внутри выпуска должны оставаться пустыми.
4. Выпустить companion UI из manifest. Новых Edge функций и изменений конфигурации в этом пакете нет.
5. Выполнить согласованную rollback-only QA проверку, затем обычную приёмку через интерфейс. Не выдавать права и не обходить guards для успешного выпуска.

prepare-release.mjs полностью локален: использует actual миграции на PGlite и файлы этого checkout, без абсолютных внешних путей и production-запросов. Hash нормализует только CRLF→LF. Семантический fingerprint совместим с PG17/18: исключены только дублирующие строки pg_constraint.contype='n', а attnotnull каждой колонки остаётся обязательной частью проверки.

## Проверки и ограничения

- 54 actual SQL сценария: auth/tenant/assigned actors, CAS/replay, неизменяемость, отказ при старой версии, настоящие UC006 upload/restore операции, DTO фронтенда, append-only Storage и metadata drift.
- 8 actual atomic batch сценариев: exact110 apply/replay, late ledger rollback, source tamper, auth drift, отсутствующая109, удалённая Storage policy, поздний побочный эффект и проверка NOT NULL/CHECK/ACL после реального review.
- Предшествующие профиль/решение создаются через actual108 RPC до batch: preservation проверяется на заполненных таблицах.
- Двухсессионная PostgreSQL concurrency не воспроизводилась: среда PGlite имеет одну connection. Row/advisory locks и последовательные stale-CAS сценарии проверены.
- SQL-тесты используют синтетические metadata объектов. Реальную загрузку/просмотр байтов, UI и production-выпуск проверяет родительская задача.
- Подготовленный work/uc-release-20261018/uc010-live-rollback.sql не входит в миграцию: он требует существующий подтверждённый QA файл, использует временные synthetic staff/group и заканчивается ROLLBACK. Локальная проверка дала 7/7 успешных утверждений и ноль оставшихся сотрудников.
