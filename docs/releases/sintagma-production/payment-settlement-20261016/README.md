## Compatibility and business rules

- Existing subscription bank orders are backfilled with the old `sub_` UUID-prefix algorithm. A trigger also derives that order for old checkout code running between SQL and Edge deployment. Existing old-priced pending invoices settle at their persisted amount, including Start 3490; new Start invoices quote 4490. Existing bank order IDs are never changed.
- Legacy invoices without a terminal binding choose the notification's terminal only among configured organization/platform terminals and still verify its HMAC. New invoices bind the terminal before bank Init. Organization-first merchant selection is preserved pending a separate product decision. Removing/rotating a terminal's credentials while orders are pending requires operational reconciliation.
- Only signed `CONFIRMED` events grant access; `AUTHORIZED` is a hold. One RPC transaction records balance, ledger, paid status, enrollment/subscription and settlement. Failure in any step or its database triggers rolls back the transaction; the handler responds 500 so the bank can retry. Refund/reversal accounting remains a separate workflow.
- Renewal extends `max(now(), paid_until)` by calendar months, clamped at the month end in UTC. Replaying a processed invoice never changes a newer plan. A first callback for an older invoice with a different plan from a newer paid purchase records money/status but leaves access unchanged and creates a durable review notification. An older purchase of the same plan adds its purchased term.
- Negotiated custom price and fixed discount come only from the protected organization row, and apply to renewal of its current plan. Choosing another plan uses its published tariff. A 12-month checkout applies the existing 15% annual discount. Manual invoice generation remains available; browser users cannot turn these into trusted bank payments or change financial fields.
- A historical paid document (or one with `paid_at`, even if a later callback changed status) without a keyed ledger is ambiguous. Its callback creates `historical_paid_without_ledger` review without a new balance credit or access grant. Existing keyed credits produce `legacy_replay` without access changes. Neither path silently repairs old partial writes: billing must reconcile bank captures, old unkeyed ledger rows and access history before making an explicit repair. Never delete settlement keys to retry a repair.
- Course payments preserve existing learning history. Missing/archived/revoked learners or expired/restricted existing enrollment create a paid review record instead of claiming automatic access succeeded. New enrollment uses the course's access duration and existing expiration trigger. Guest identity provisioning is unchanged.
- Separate checkout submissions remain separate bank orders and have distinct document numbers. Browser retries of the same purchase intent are not automatically merged; payment callback idempotency is per persisted order.

## Validation

50 local tests pass: 20 execute the actual ledger and settlement migrations in PGlite, 14 invoke the actual webhook, 12 invoke the actual checkout/shared tariff contract, and four preserve ledger structure/permission assertions. SQL tests cover both original reproductions (early renewal and old callback downgrade), a new unseen older invoice, calendar/leap ends, historical paid/no-key replay, old checkout compatibility, enrollment failure rollback, paid-trigger failure rollback, retry, immutable browser invoice fields and service-only settlement. The release SQL copies are checked against the migration sources and diagnostics execute in the fixture database. Handler tests replace all network access; no production records or secrets are loaded. Both extracted handlers also pass an isolated TypeScript check.

PGlite serializes its local connection and does not prove simultaneous multi-session lock scheduling. Production concurrency relies on the explicit organization-then-document row lock order shared with the existing ledger/debit operations and unique settlement/ledger indexes. A staging PostgreSQL concurrency smoke test is recommended before rollout.
