### Cloud storage ownership gate

`CREATE POLICY ON storage.objects` requires actual policy-management authority. The first local preflight incorrectly required table ownership for this operation and was too strict for managed Supabase. Supabase's official `supautils.policy_grants` mechanism can already delegate policy management without ownership. Fresh live read-only evidence confirmed a server-defined setting (`context=sighup`, `vartype=string`) whose `postgres` entry explicitly includes `storage.objects`; the selected executor/current role was `postgres`. The coordinator saved that observation privately in `D:/Codex/work/sintagma-queue/work/s029-policy-capability.json`.

The corrected preflight retains ownership checks for `public.courses` and `public.test_attempt_sessions`, where the migration performs ALTER TABLE. Its separate `storage_policy_capability` check accepts table ownership or an existing `pg_settings` entry named `supautils.policy_grants` with `context=sighup`, `vartype=string`, and a JSON array under the exact current-user key containing `storage.objects`. No server setting, owner, grant or membership is changed. If neither capability exists, stop and use the provider's supported route; do not remove this check merely to continue.

Primary sources: [Supabase's supported Storage-policy operations](https://supabase.com/changelog/34270-restricting-access-on-auth-storage-and-realtime-schemas-on-april-21-2025), [Supautils policy delegation](https://github.com/supabase/supautils#table-ownership-bypass), [exact-current-role policy check](https://github.com/supabase/supautils/blob/master/src/policy_grants.c), and [server-managed SIGHUP setting](https://github.com/supabase/supautils/blob/master/src/supautils.c). [Lovable's documented policy-change route](https://docs.lovable.dev/features/database#row-level-security-rls-policies) remains available if a native migration route is needed.

The repository's `drizzle.config.ts` names the provider-managed `LOVABLE_DB_MIGRATION_URL`; its value is not in this package. The prior S027 migration under `drizzle/migrations` is evidence that the provider uses this path, but S027 did not create policies on `storage.objects` and therefore does not prove that path has the required storage ownership. Before using it, obtain read-only evidence through the native migration connection. The standalone wrapper must not be nested unmodified inside a provider-managed transaction: a reviewed adapter would omit only its outer transaction boundaries while retaining exact source, integrity check, locks, hard preconditions and ledger handling inside the provider's atomic transaction. Keep exactly one canonical pending migration, not independent Supabase and Drizzle copies that can both apply.

## Integrity and local validation

The original migration is embedded once, byte-for-byte, inside a unique SQL dollar-quoted string. Its SHA256/length and LF-normalized MD5 are in `validation.json` and the wrapper header. PostgreSQL transport may normalize CRLF to LF; the integrity check and ledger postcheck normalize **only CRLF**, without trimming or other rewriting. Replaced/new function body checks use the same normalization.

The two internal `_final_test_photo_*` helpers explicitly deny PUBLIC/anon/authenticated. Their service-role EXECUTE privilege is not constrained by the source migration and may depend on provider default privileges; postcheck accepts either service-role state for these two only. All explicit grants/revokes remain checked. Local validation exercises both default service grants and their absence, including broad default table/function grants to API roles.

`prepare-and-validate.mjs` regenerates this package from the unchanged source and existing `scripts/test-final-test-photo.mjs` fixture. It uses an already installed PGlite, installs nothing and makes no network calls. It verifies commit, exact ledger, catalog/postcheck, replay refusal, full DDL/function/policy rollback after an artificial ledger error, and refusal after a live-source drift simulation. Ten SQL predicate cases also verify valid owner/provider delegation, wrong role/table/context/setting/type/JSON shape and missing configuration. PGlite does not implement the Supautils hook: these ten cases validate our read-only capability predicate, not the provider's extension implementation. Run with the D-hosted Node executable from the repository root. The default dependency path is on D; `PGLITE_MODULE_PATH` may point to another existing installation. This is not real multi-connection lock testing, provider transport validation, or evidence that notifications reached PostgREST.

## Recovery

Before COMMIT: the wrapper is transactional, including bucket metadata, policies, functions and ledger. If execution failed, independently verify absence/unchanged state before any retry; an aborted editor transaction may require `ROLLBACK`.

After COMMIT: preserve the new table, bucket, photographs and session audit. If the option causes a problem, disable it only for affected courses and correct forward. Existing sessions keep their snapshotted requirement and must retain valid RPC/photo links. With all course switches off, the prior frontend can operate against the additive schema; reverting only the frontend while courses remain enabled leaves the old UI unable to satisfy the server photo gate.

Do not drop photo/session objects, remove security guards, restore legacy learner write access, or blindly restore old functions/data after new photo sessions exist. Any targeted restoration must reconcile records created after the backup. `backup-functions.sql` preserves evidence for that decision; it does not authorize destructive recovery.
