# ГОРЭЛТЕХ: сохранение пакета без повторной партии

## Что исправлено

Раньше после сетевой ошибки интерфейс мог разрешить новое формирование по обычному
перечитыванию списка. Пустой или старый список не доказывает, что первая серверная
операция остановилась: поздний commit мог создать вторую партию.

Теперь сохранение девяти Word-документов получает UUID операции до отправки.
Сервер сохраняет пакет и подтверждение операции одной транзакцией. Повтор с тем же
UUID возвращает исходный результат; новые поля повторного запроса не заменяют уже
созданную партию. Автоматического повтора записи нет.

В браузере сохраняются только UUID незавершённой операции и UUID-подтверждения,
без ФИО, документов, паролей или содержимого форм. Подтверждение одной операции
не удаляет указатель более новой операции другой вкладки. Ошибка хранилища
показывается пользователю, а не превращается в успешное сохранение.

## Как восстановиться после ошибки

1. Нажать **«Проверить операцию и перечитать список»**. Разрешить новую операцию
   может только подтверждение именно исходного UUID, не сам список документов.
2. Если завершение неизвестно, можно нажать **«Повторить сохранение без дубликата»**.
   Используется прежний UUID. Первый сохранённый пакет этой операции имеет приоритет.
3. Для изменённого комплекта сначала подтвердить старую операцию, затем начать новую.
   Номер сохранённой партии не означает, что она до сих пор является текущей.

Закрытие вкладки/раздела и перезагрузка не должны забывать незавершённый UUID.
Dry-run по-прежнему не сохраняет документы, не создаёт UUID записи и не снимает
блокировку неизвестной операции.

## Сервер и порядок выпуска

- Edge revision: `goreltech-group-package-server-facts-v20`.
- Новая миграция: `20260904160000_goreltech_document_operations.sql`.
- RPC `get_goreltech_document_operation` и
  `create_goreltech_group_document_batch_once` доступны только `service_role`.
  Actor, право `documents.manage`/владелец/администратор и точные tenant/group
  проверяются повторно сервером. Другой actor не получает чужое подтверждение.
  Для сотрудника обязательна действующая запись `org_staff`: срок не задан либо
  ещё не истёк. Edge dry-run использует `can_access_organization` с JWT пользователя.
- Обычная таблица подтверждений недоступна напрямую через клиентскую API.
- При недоступной миграции сохранение останавливается до загрузки файлов.
  Отката на старую неидемпотентную RPC нет. Старые вкладки должны обновить интерфейс.
- После начала RPC сетевой сбой не разрешает удалять загруженные файлы: транзакция
  могла продолжаться. Возможные непривязанные файлы не удаляются автоматически.

Выпуск: подтверждённый backup/restore → проверка точного набора additive migrations
(включая предыдущие расписание и отметки) → SQL → Edge v20 → согласованный frontend
через GitHub/Lovable/Timeweb → реальная проверка в кабинете ГОРЭЛТЕХ с перезагрузкой.
Не выкатывать все накопленные миграции без отдельной сверки. Не публиковать frontend
раньше требуемого сервера. Откат frontend/Edge не требует удаления таблицы операций.

## Проверки и ограничения доказательств

Проверяются: строгий save acknowledgment; неизвестный/потерянный ответ;
отдельный read-only status; старые ревизии; повтор того же UUID; полный unmount;
поздние ответы чужой группы; ошибки localStorage; гонка старого ACK с новой операцией;
компиляция исходного Word без изменения шапки и стилей.

`scripts/verify-goreltech-document-operations.mjs` исполняет новую миграцию и
существующую настоящую batch RPC в локальном PGlite. На момент подготовки проверено
80 условий, включая rollback пакета/receipt/is_current и истёкший доступ. Auth helpers в этом harness
тестовые; это не доказательство production RLS или конкуренции нескольких PostgreSQL
сессий. Два независимых новых намерения из разных вкладок не считаются одной операцией.

Локальные gates: общий набор 169 тестов; после усиления ACK — 81 тест в четырёх
перекрывающихся файлах; после исправления expiry — 18 Edge contract tests.
Итого покрыты 176 уникальных сценариев в семи файлах. App TypeScript, Deno check и
ESLint завершились успешно (в полном изменённом наборе ESLint — 11 предупреждений,
без ошибок). Финальная сборка и SHA выпуска фиксируются отдельно после commit.

Локальные доказательства на D:

- `D:/CodexTmp/sintagma-operation-v20-all-tests-20260904.json` — исходный общий прогон.
- `D:/CodexTmp/sintagma-operation-v20-ack-delta-20260904.json` — финальная проверка ACK.
- `D:/CodexTmp/goreltech-journal-visual-20260904/02-demo-marks.pdf` — Word-export,
  одна страница; синтетические ученики и отметки, **не документ реальной группы**.
  SHA256 `EE8E3B7E7620EA9FFB2D7DEDFF15377A90266BAA9394575B5CD2B4D31C6232C8`.
- `02-demo-marks.png` рядом — визуализация того же PDF. Правая граница таблицы
  присутствует в PDF. Окно Word отображало её неполно; исходный OOXML не менялся.
- Из 19 ZIP-частей исходного шаблона изменён только `word/document.xml` для подстановки
  данных; остальные 18, включая шапку, изображение и стили, побайтно идентичны.

Не заявляются завершёнными: production E2E, официальные номера/итоговый статус,
все девять визуально проверенных документов реальной группы, XML Минтруда/API,
полная готовность всей платформы. Интерфейс ученика и исходные DOCX не изменены.
