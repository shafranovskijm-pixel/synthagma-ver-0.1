# Отложенное задание Lovable: быстрый холодный аутрич «44-ФЗ ДФО»

Дата фиксации: 12 августа 2026 года.

## Цель

Доработать production-модуль рассылок СИНТАГМА для безопасного управляемого холодного B2B-аутрича организации ЧОУ ДПО «ИНСТИТУТ РАЗВИТИЕ 2000»: импорт 203 ящиков `@torgi.com.ru`, персонализация по ответственному лицу, контрольная выборка и, только после успешного теста, обработка 812 уникальных email за двое суток.

Это задание не разрешает запуск кампании, публикацию релиза или импорт секретов в production без отдельной проверки результата.

## Подтверждённые ограничения текущей реализации

1. `run-email-campaign` проходит весь pending-список циклом с фиксированной паузой около 1,5 секунды, поэтому не умеет выдерживать суточные и получасовые слоты.
2. Квота резервируется на весь pending-остаток, а не на разрешённую порцию текущего слота.
3. `process-scheduled-campaigns` выполняет одноразовый запуск и не является повторяющимся планировщиком отправки.
4. Отправители добавляются по одному; защищённого пакетного импорта нет.
5. Квоты считаются по отправителю, но нет обязательного совокупного лимита домена и IP.
6. Текущий gate `consent_confirmed` не описывает режим холодного B2B-аутрича. Нужны явные режимы кампании и фиксация основания оператора без ложного утверждения, что каждый получатель заранее подписался.
7. Нет надёжного атомарного захвата запуска; параллельные вызовы могут попытаться отправить одно задание дважды.
8. Последний production seed-тест `ngal@torgi.com.ru` завершился `missing`; автопрогрев выключен.
9. Ответы с 203 адресов нельзя безопасно вести без единого inbox/reply polling и назначения ответственного.

## Обязательная реализация

### 1. Режим кампании и suppression

- добавить `campaign_mode`: `cold_outreach` или `permission_marketing`;
- для `cold_outreach` хранить подтверждение оператора о профильности базы, корректности отправителя и обработке отказов;
- не требовать фиктивного opt-in каждого адресата;
- добавить глобальный suppression list организации по нормализованному email;
- обрабатывать ссылку отписки, ответ с отказом, bounce и complaint до следующей отправки;
- запретить повторное добавление suppression-адреса через импорт.

### 2. Очередь и идемпотентность

- создать send-job очередь с полями `campaign_id`, `recipient_id`, `sender_account_id`, `not_before`, `status`, `attempt_count`, `claimed_at`, `claim_token`, `smtp_message_id`, `last_error`;
- уникальность как минимум по `campaign_id + recipient_id + step_no`;
- атомарный захват доступных заданий через RPC/транзакцию с `FOR UPDATE SKIP LOCKED`;
- состояние менять идемпотентно; повторный worker не должен повторно отправлять письмо;
- выбирать только ограниченную порцию текущего слота, а не резервировать всю очередь;
- retries выполнять с backoff и без списания delivery-credit до подтверждённого SMTP acceptance.

### 3. Общий лимит инфраструктуры

- считать лимиты одновременно по организации, домену, IP/MX-инфраструктуре, отправителю и кампании;
- ограничение отправителя не может увеличить общий доменный лимит;
- хранить фактическое число попыток, SMTP accepted, hard bounce, complaint, seed inbox/spam/missing и replies;
- при неизвестном IP применять общий лимит домена/MX как обязательный.

### 4. Безопасный пакетный импорт отправителей

- доступ только глобальному администратору или владельцу организации с отдельным правом;
- принимать не более 50–100 строк за один запрос;
- проверять домен, формат email, SMTP/IMAP host/port/TLS;
- пароль шифровать сразу на сервере существующим механизмом;
- не возвращать пароль в ответе, не писать его в логи, аналитику, ошибки или `localStorage`;
- после отправки формы очищать пароль из состояния клиента;
- идемпотентность по `organization_id + normalized_email`;
- все импортированные ящики создавать `inactive`;
- пакетный тест SMTP/IMAP выполняет только авторизацию, не отправляет письма, не читает и не меняет входящие;
- ограничить параллелизм проверки до 5 соединений;
- выдавать отчёт по строкам без секретов: создан, уже существует, SMTP OK/error, IMAP OK/error.

### 5. Пул отправителей и ответы

- явные состояния `inactive`, `testing`, `active`, `paused`, `disabled`;
- в кампанию попадают только вручную активированные отправители с успешными SMTP/IMAP-тестами;
- закреплять получателя за одним стабильным отправителем на всю цепочку;
- перед массовым использованием многих ящиков реализовать IMAP reply polling/единый Unibox;
- после ответа останавливать все следующие шаги и назначать диалог ответственному менеджеру.

### 6. Персонализация

- брать только разрешённые ключи из `custom_data`;
- обязательные поля: `greeting`, `organization_short`, `relevance_phrase`, `format_hint`, `unsubscribe_url`;
- при неразрешённой переменной или пустом обязательном значении не отправлять задание;
- показывать предпросмотр итоговой темы и текста для каждой строки;
- поддержать нейтральный шаблон для общих адресов без произвольного выбора одной организации;
- не добавлять случайный spin-текст для обхода фильтров.

## Режимы скорости

### Контрольный режим

- 20 писем в сутки суммарно по домену;
- окно 09:00–20:00 МСК;
- не чаще одного задания в часовой слот, пока не набрана статистика;
- первая выборка — строки `pilot_batch=1`;
- окончательный seed-статус проверять не раньше чем через час.

### `fast_2_day`

Режим выключен по умолчанию и включается вручную только после успешного контрольного дня.

- 406 доставок в сутки, два дня;
- не более 2 писем на ящик в сутки;
- минимум 5 часов между письмами одного ящика;
- общий лимит 406 на домен/IP в сутки;
- окно 09:00–20:00 МСК;
- до 19 заданий на получасовой слот, равномерно распределённых внутри слота;
- один получатель получает только одно первое касание;
- режим 4–5 писем с каждого из 203 ящиков не используется для маскировки общего объёма.

### Автопауза

Немедленно остановить кампанию и новые задания домена при любом условии:

- complaint больше нуля;
- seed-письмо попало в spam;
- `missing` подтверждён после одного часа;
- SMTP/IMAP auth error у активного ящика;
- hard bounce не менее 2% на статистически достаточной отправке или два последовательных hard bounce в малой выборке;
- превышен лимит организации, домена, IP/MX, отправителя или слота;
- недоступна проверка suppression list;
- в итоговом шаблоне осталась переменная `{{...}}`.

## Тесты и release gates

- unit: расчёт часовых/получасовых слотов, часовых поясов, доменного и sender cap;
- unit: переменные, нейтральный fallback, suppression, idempotency key;
- integration: два параллельных worker не получают одно send-job;
- integration: импорт не возвращает и не логирует пароль;
- integration: inactive sender никогда не выбирается;
- integration: complaint/bounce/missing ставят домен и кампанию на паузу;
- end-to-end: 20 пилотных строк, preview, постановка в очередь, отмена, пауза и возобновление;
- production: отдельно подтвердить frontend Publish, миграции, Edge Functions/worker, cron/scheduler, secrets и фактические данные нужной организации;
- после публикации перезагрузить production, войти в режим просмотра ЧОУ ДПО «ИНСТИТУТ РАЗВИТИЕ 2000» и повторить тест без чтения тел входящих и без искусственных ответов.
